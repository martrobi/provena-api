# ADR 0014: Source Quantity Allocation v1 (retained per-plot quantity attribution within the single lot)

- Date: 2026-10-23
- Decision status: Accepted
- Implementation status: **Implemented** (backend only; the separate client has not adapted). Source Quantity Allocation v1 was introduced by backend implementation commit `7770612e1e3b96edf07c62737ce1414dfcd90fb8` (`7770612`, `feat(api): add source quantity allocation`), directly on top of `fd6683a`.
- Decision owner / approval evidence: the owner specified the model and rules in the Source Quantity Allocation v1 design and implementation requests (`ContributionPlot.AllocatedQuantity`, the silent-clear protection, completeness policy v3, fingerprint version 2, snapshot schema version 2, the migration and its Down guard) and, in a follow-up, the OpenAPI handling of the versioned snapshot. The plan artifact itself is not retained in the repository; this ADR documents the **implemented** decision.
- Supersedes / superseded by: supersedes nothing. It **amends** [ADR 0007](0007-case-dossier-lot-attribution.md) (per-plot quantity was deferred there; the grain "quantity is per producer, not per plot" now has one optional, retained refinement), [ADR 0008](0008-completeness-facts-and-reviewed-history.md) (the fingerprint and review snapshot gain a second supported version; the completeness policy moves to version 3) and, narrowly, [ADR 0010](0010-quantity-reconciliation-v1.md) (its statements that fingerprint and snapshot stay version 1 were true for that slice and are no longer true for **new** reviews; Quantity Reconciliation itself is unchanged).

## Context and evidence

Before this decision (observed at `fd6683a`):

- A `LotContribution` states one producer's quantity within one immutable `CaseLot` version; a `ContributionPlot` pins that contribution to one plot at one exact `PlotRevision` and "carries no quantity" ([ADR 0007](0007-case-dossier-lot-attribution.md), `Domain/Dossiers/CaseDossier.cs`). Per-plot quantity allocation was listed as undecided in ADR 0007 and ADR 0010 and as open in [EUDR_GAP_ANALYSIS](../EUDR_GAP_ANALYSIS.md) G14/G15.
- The provenance model could therefore say *which* plots a producer's material came from but not *how much* of the lot came from each plot, so later per-source questions (country-weighted quantities, findings per source, DDS coverage) had no retained quantity to attach to.
- `CaseLot`, `LotContribution` and `ContributionPlot` are fully immutable apart from the `CaseLot.SupersededAtUtc` retirement; every material change writes a new lot version under the case lock with `expectedCurrentLotId` (ADR 0007 amendment). The fingerprint (`DossierFingerprint`, version 1) and the review snapshot (`ReviewSnapshot`, schema 1) covered the lot, producers and plot links but no plot quantity.
- `QuantityReconciliation` (ADR 0010) answers a different question (shipment, supplier-confirmed, lot and producer quantities agree) and must not be redefined.

## Decision

**`ContributionPlot.AllocatedQuantity decimal?` is the retained grain of source quantity allocation.** One row of `ContributionPlot` is exactly `CaseLot version × LotContribution (producer) × ProductionPlot × pinned PlotRevision`: the smallest unit that already names a concrete source at an exact revision and that is already immutable and versioned with the lot. Storing the quantity there means the allocation is retained with the exact lot version it belongs to, is covered by the existing composite foreign keys, tenant boundary, immutability guard and `Current()` semantics, and cannot be rewritten later. There is no new entity, table, route or concurrency token.

**Storage and meaning.**
- `numeric(20,6)`, **nullable**, no default, same range and precision rules as every other lot quantity. `null` means "allocation not recorded". When present it is `> 0` (zero is invalid: a source that contributes nothing is not linked).
- There is **no unit column**: the unit is the contribution's unit, which the validator forces to equal the lot unit.
- **No inference and no backfill.** A single-plot contribution is never given the contribution quantity automatically, no equal split is made, and no existing row is touched: every legacy row stays `null` and every legacy lot version reads as `NotRecorded`.
- Comparison is exact decimal equality (`10` equals `10.000000`); **no unit conversion, no tolerance, no percentages or shares.**

**Write-time invariants** (`CaseLotValidator`, `ContributionPlotValidator`, `CaseDossierService`; all 400):
- `allocatedQuantity` per plot link: `> 0`, `< 100000000000000`, at most 6 decimals (`PrecisionScale(20, 6)`).
- **All or none:** within one lot version either every plot link carries `allocatedQuantity` or none does. A partial set is rejected (validation error on `Contributions`: "Every plot link must carry an allocated quantity when any plot allocation is recorded.").
- **Per contribution:** the sum of its plot allocations must not exceed the contribution quantity (400, `errors.reason` `PlotAllocationExceedsContribution`, safe metadata `producerId`). Under-allocation **may be stored** (a draft state).
- `Σ contributions ≤ lot quantity` is unchanged (ADR 0007). A contribution without plot links stays storable under the existing model rules; once any allocation is recorded elsewhere it is derived as `MissingData`.
- **An allocation change is a new immutable `CaseLot` version** written through the existing `PUT .../dossier/lot`; the previous version keeps its values in the lot history.

**Silent-clear protection** (`CaseLotInput.ClearSourceAllocations`, default `false`; `CaseDossierService.EnsureAllocationsNotSilentlyChanged`). A client that omits the new field must never erase recorded allocations, and Provena never keeps them implicitly either. After the `expectedCurrentLotId` check and before the identical-resubmission no-op:
- current lot **has** recorded allocations, incoming request has values: they are validated normally and replace the old values through a new version;
- current lot has recorded allocations, incoming request has all allocations `null` or omitted and `clearSourceAllocations` is not `true`: **400, `errors.reason` `SourceAllocationsNotSupplied`**, nothing written;
- `clearSourceAllocations: true` with every `allocatedQuantity` `null` or omitted: a normal new version whose allocation is `NotRecorded`; the version with the values stays in the history;
- `clearSourceAllocations: true` together with any `allocatedQuantity` value: 400 validation error on `ClearSourceAllocations` ("clearSourceAllocations cannot be combined with allocated quantities.");
- the current lot has **no** recorded allocation (or no lot exists) and `clearSourceAllocations` is `true`: **400, `errors.reason` `ClearSourceAllocationsNotApplicable`**;
- nothing recorded and nothing supplied is an ordinary save (an identical resubmission is the idempotent no-op).

There is no silent preservation, no silent clearing and no silent retry.

**Derived read model `SourceAllocation`** (`Services/SourceAllocation.cs`, pure, in the style of `ProductionCoverage` and `QuantityReconciliation`). Derived on every read, export and evaluation; **never stored, never fingerprinted as a result (its inputs are fingerprinted), never overridden, and not a check of `QuantityReconciliation`**. It is quantity attribution within the single-lot pilot; it is not a legal net-mass, yield, country-risk or compliance finding.
- Statuses: `NotRecorded`, `MissingData`, `OverAllocated`, `UnderAllocated`, `Matched`.
- `NotRecorded`: no plot link of the lot version carries a value (every legacy lot, also a lot without contributions).
- Otherwise, for each contribution: `OverAllocated` if the sum of its plot allocations exceeds the contribution quantity; else `MissingData` if it has no plot link or any of its links has no value; else `UnderAllocated` if the sum is below the contribution quantity; else `Matched`.
- Lot status, in this precedence: `NotRecorded`; `OverAllocated` if the plot total exceeds the lot quantity or any contribution is over-allocated; `MissingData` if any contribution is; `UnderAllocated` if the plot total is below the lot quantity or any contribution is under-allocated; else `Matched`. So `Matched` needs every contribution fully allocated to its plots **and** the plot total equal to the lot quantity: contributions that together fall short of the lot are `UnderAllocated` even when each is fully allocated (`LOT_RECONCILED` reports the same gap separately).
- `SourceAllocationDto { status, lotQuantity, unit, allocatedQuantity, unallocatedQuantity, contributions[] }`, each contribution `{ producerId, contributionQuantity, allocatedQuantity, unallocatedQuantity, status }`. `unallocatedQuantity` is the quantity minus the allocated total (negative only in the defensive over-allocation case). Per-plot values stay on `ContributionPlotDto.allocatedQuantity` and are not duplicated.
- `OverAllocated` cannot be produced through the API (writes reject it); it exists as a defensive status for rows written by other paths.

**Completeness policy version 3.** `CompletenessPolicy.Version` is `"3"`. A new Quantity item `SOURCE_ALLOCATION_RECONCILED` (subject `CaseLot`, no subject when there is no lot) follows `LOT_RECONCILED`: `NotRecorded` → `NotApplicable`, `Matched` → `Satisfied`, `MissingData` → `Missing`, `UnderAllocated` and `OverAllocated` → `Invalid`. Product meaning: **per-plot allocation stays optional**, but once allocation is recorded, inconsistent or incomplete allocation makes the item `Missing`/`Invalid`, makes `dataCoverage` `Incomplete` and, through the **existing** blocking-item rule of `ReviewPreconditions`, blocks `AcceptedAsCompleteUnderPolicy`. `ReviewPreconditions` is unchanged; `ConfirmedOutsideRegulatoryScope`, `ConfirmedUnsupportedFlow` and `ReturnedForCorrection` keep their existing semantics; there is **no close-specific allocation gate** (a changed allocation is a new lot version, which stales the review, and the existing `StaleReview` close check already applies). A policy-version change alone only sets `policyChanged` on existing reviews.

**Fingerprint version 2.** Fingerprint version 1 is **frozen**: its canonical output is byte-for-byte unchanged (the golden fingerprint `2cc06ed492c0914bcd43c7e0e779eb278077addf6ba90f87fbd9b792807df5a1` and the seven section hashes of the fixed fixture are still pinned by `Fingerprint_v1_output_is_unchanged_by_quantity_reconciliation`, now computed with an explicit version 1). Version 2 follows the existing canonical form and adds the canonical `allocatedQuantity` (invariant decimal without trailing zeros, `null` when not recorded) after the production period of every plot link in the `Lot` section, and `fingerprintVersion: 2` in the envelope. `DossierFingerprint.CurrentVersion` is 2 and `SupportedVersions` is `[1, 2]`. New reviews are stored with version 2; a review keeps recomputing with its **stored** version (`ReviewFreshnessService`), and an unknown stored version is still rejected. No stored review is rewritten. Even a version-1 review becomes `Stale` (section `Lot`) after an allocation change, because any allocation change writes a new `CaseLot` version and the version-1 `Lot` section contains the lot id. The derived `SourceAllocation` result itself is not fingerprinted.

**Review snapshot schema version 2.** The version-1 snapshot contract (`CaseRevisionSnapshotV1`, `SnapshotLotV1`, `SnapshotContributionV1`, `SnapshotPlotLinkV1`) is unchanged and old schema-1 snapshots stay readable exactly as stored. Schema 2 (`CaseRevisionSnapshotV2`, `SnapshotFactsV2`, `SnapshotLotV2`, `SnapshotContributionV2`, `SnapshotPlotLinkV2`) is schema 1 plus `allocatedQuantity` on each plot link. `ReviewSnapshot.SchemaVersion` is 2 for new reviews and `SupportedVersions` is `[1, 2]`; an unknown version is rejected. A schema-1 snapshot reads allocation as `null` and therefore derives `NotRecorded`. Reviewed exports derive `SourceAllocation` from the retained snapshot only and never resolve allocation from live lot, contribution, plot or revision rows.

**Versioned snapshot in the API contract.** `ReviewDetailDto.snapshot` (and `ReviewExportDto.snapshot`) is typed `IReviewSnapshot`, a union of the exact version-1 and version-2 shapes. Serialization is polymorphic **without** a discriminator: the runtime JSON carries `schemaVersion` (1 or 2), selects its shape by it, and carries **no `$type` member** (the wire JSON did not change for a version-1 snapshot). The generated OpenAPI document describes the union as `anyOf` the two shapes; the generator's `discriminator: "$type"` does not exist on the wire and is removed by a schema transformer in `Program.cs`, and the schema description states that `schemaVersion` selects the shape. Clients must use `schemaVersion`; no JSON discriminator is invented.

**API and concurrency.** Additive and optional: `ContributionPlotInput.allocatedQuantity`, `CaseLotInput.clearSourceAllocations`, `ContributionPlotDto.allocatedQuantity`, `CaseLotDto.sourceAllocation` (lot history exposes the same retained values per version). No new route. `expectedCurrentLotId` is reused unchanged (`null`/omitted = no lot was loaded). Order inside the transaction: case lock (404) → mutability (409) → body validation (400) → load the current lot → **`expectedCurrentLotId` (409 `LotHistoryChanged`)** → silent-clear protection (400) → identical-resubmission no-op (now including `allocatedQuantity`) → `lotReference` uniqueness → source locks and checks → per-contribution allocation check (400 `PlotAllocationExceedsContribution`) → supersede and insert. A stale id therefore wins over the silent-clear 400 and is still checked before the identical no-op; `LotHistoryChanged` remains the only optimistic-concurrency conflict and there is no second token.

**Database.** One additive migration `20261022221125_SourceQuantityAllocation`: `ContributionPlots.AllocatedQuantity numeric(20,6) NULL` and `CK_ContributionPlots_AllocatedQuantityPositive` (`"AllocatedQuantity" IS NULL OR "AllocatedQuantity" > 0`). No default, no backfill, no new foreign key or index, no tenant-key change (the column sits on a row whose composite tenant keys are unchanged). The cross-row rules (all-or-none, sum within the contribution) are API rules, like the production-period rules. **Down** starts with a `DO $$` guard that raises `Source allocations exist; rollback would destroy history` while any `ContributionPlots.AllocatedQuantity` is not null, so the rollback is not universally reversible: it succeeds only when no allocation was ever recorded or all were removed by other means; legacy null rows never block it. The model snapshot was produced by `dotnet ef migrations add` and is not hand-patched.

**Exports.** Working export: `dossier.currentLot.sourceAllocation` and `dossier.currentLot.contributions[].plots[].allocatedQuantity` through the existing dossier DTO; no top-level duplicate; `summary.csv` unchanged. Reviewed export (`review.json`): the stored `snapshot` (schema 2 carries `allocatedQuantity`; schema 1 does not), plus the siblings `sourceAllocation` (`SourceAllocationDto` derived only from the snapshot's lot facts; for a stored schema-1 review it is a `NotRecorded` result with the lot's quantities, and it is `null` only when the review has no lot) and `sourceAllocationScope` ("Derived attribution of the lot quantity to the recorded production plots (exact decimal equality in the lot unit; no conversion, tolerance or percentage). Quantity attribution only; not a legal net-mass, yield or compliance determination."). Neither sibling adds anything to the stored snapshot or the fingerprint.

Deliberately undecided: whether allocation should become mandatory, legal net-mass and yield semantics, unit conversion, tolerance, percentages, multi-lot/split/merge/processing lineage, cross-case plot capacity, country risk, legality and deforestation findings per source, DDS partial coverage and Annex I scope.

## Alternatives considered

- **A separate allocation entity or table (for example `SourceAllocation` rows or `ProductionSource`/`ProductionEvent`).** Rejected: it duplicates `ProductionPlot` + `PlotRevision` + `ContributionPlot` (ADR 0007 amendment), needs its own tenant keys, immutability guard and versioning, and could drift from the lot version it describes.
- **Mutable allocation rows or an allocation-specific route.** Rejected: allocations would be rewritable after a review, and a second write path would need its own concurrency token and lock order. The existing `PUT dossier/lot` with `expectedCurrentLotId` keeps one atomic, versioned write.
- **Percentages or shares.** Rejected: rounding breaks exact decimal equality, and a share of what base would be ambiguous.
- **A separate unit column.** Rejected: it would only make a unit mismatch possible; the lot unit is the unit.
- **Allocation on `LotContribution`.** Rejected: that row already is the producer quantity; the plot is the finer grain.
- **A fourth Quantity Reconciliation check.** Rejected: it answers a different question (lot to sources) and would change `Matched` and the `ExternalDdsCompleted` close semantics of ADR 0010.
- **Backfill or inferred allocation (equal split, single plot equals contribution).** Rejected: it would fabricate facts and change the fingerprint of Current reviews.
- **Emitting `allocatedQuantity` conditionally inside fingerprint version 1.** Rejected by the owner: version 1 must stay byte-for-byte frozen; version 2 was added instead.
- **Mutating the version-1 snapshot types.** Rejected by the owner: schema 2 was added and schema 1 stays readable as stored.
- **A JSON `$type` discriminator for the snapshot union.** Rejected: `schemaVersion` already is the discriminator and the wire JSON must not change.
- **Mandatory allocation, a close-specific allocation gate, tolerance or conversion.** Out of scope for v1.

## Consequences

- Every plot link of a lot version can say how much of the lot it supplies; history keeps every earlier version. Later features can attach to `ContributionPlot` ids or to the pinned revision with a quantity (see below) without another redesign.
- Policy version 3 and fingerprint/snapshot versions 2 are visible to clients: new reviews report `fingerprintVersion` 2, `snapshotSchemaVersion` 2 and `policyVersion` "3"; old reviews keep their stored values and report `policyChanged: true`. A client must read `ReviewDetailDto.snapshot` by `schemaVersion`.
- A client that re-saves a lot with recorded allocations but without `allocatedQuantity` now gets 400 `SourceAllocationsNotSupplied` instead of silently dropping them. Recording or changing allocations stales the latest review (section `Lot`).
- Rollback of the migration is possible only while no allocation is recorded.
- Allocation is quantity attribution, not compliance: `Matched` is not "compliant", "legally valid" or "verified net mass".

Future attachment points (not implemented): country risk by source country can group the allocated quantity by the pinned `PlotRevision.CountryCode`; legality/deforestation findings can reference a `ContributionPlot` (version-exact) or the pinned revision through the review pin; DDS coverage can reference the same rows through `ExternalDdsRecord → ReviewId → CaseLotId`; split/merge lineage can later treat the allocation as the leaf quantity at the source. Each needs its own decision and ADR.

## Revisit trigger

A decision to make allocation mandatory or to gate closing on it; legal net-mass, yield, unit-conversion or tolerance rules; multi-lot, split, merge or processing lineage; cross-case plot capacity; or country-risk, legality, deforestation or DDS-coverage features that need per-source quantities.
