## Context and evidence

Slices 1-4 retain evidence, model producer/plot provenance and record a case's lot with pinned plot revisions. Provena still cannot say whether the *working* dossier is factually complete under a stated policy, nor exactly what an accountable human reviewed. Party and product facts live in shared, in-place-edited catalogue rows (`CatalogService` takes no case lock), `Organization` has no operator identity, and nothing records the human assessment of scope or the recipients. Source: `Domain/Compliance/*`, `Data/AppDbContext.cs`, `Services/CaseMasterDataService.cs`, `Services/CaseApplicabilityService.cs`, `Services/ApplicabilityDerivation.cs`, `Data/Migrations/*CompletenessFacts*`.

## Decision

Implemented in commit 1:

- **Case-owned master-data copy with explicit refresh (`CaseMasterDataVersion`).** The values a case relies on (operator, supplier, product) are copied into an immutable, versioned, case-owned row (sequential `Number`, one current per case via a partial unique index, one-way `SupersededAtUtc`). Shared catalogue edits never change the copy; only a deliberate, audited `POST .../master-data/refresh` creates the next version (`CaseMasterDataRefreshed`). The refresh runs under the case lock on a case that is still editable, reads the **current shipment** under that lock, and locks `OperatorProfile`, the shipment's `Supplier` and `Product` `FOR SHARE`. If every copied field (context fields included) equals the current version it returns that version with no new row and no audit event.
- **Shipment binding.** `SupplierId`/`ProductId` of the copy come from the case's current shipment, never from the client, and carry tenant-safe composite FKs. A shipment may change supplier/product while the case has no dossier, so the copy is only valid while `copy.SupplierId == shipment.SupplierId && copy.ProductId == shipment.ProductId`; this is exposed as `shipmentMatch` and enforced on applicability saves (409 until refreshed). The Slice 4 shipment lock is unchanged.
- **Drift is advisory.** `drift` compares the live operator profile and the copy's own supplier and product with the copy over fact-bearing fields only (`ProductName` and `ProductCatalogueDescription` are context). It is computed on read, never mutates the case, never refreshes and never uses `UpdatedAtUtc`. It blocks `AcceptedAsCompleteUnderPolicy` but is never part of the fingerprint.
- **Applicability is a recorded human assessment, not a determination by Provena.** Immutable versions; the assessed product identity (`AssessedProductId`, `AssessedCnCode`, `AssessedCommodity`) is copied by the server from the **matching master-data copy**, never from the client and never from the live `Product`. `ProductDescription` is the authoritative assessed trade description and is distinct from the reusable catalogue `Product.Description`. `OperatorRole` is `Operator` or `OtherUnsupported` (the latter always requires a role description and always derives `UnsupportedFlow`).
- **Derived applicability status** (pure function `ApplicabilityDerivation.Derive`, not a rules engine, never inferred from CN format): `NotRecorded`, then `ProductChanged` when the assessed `ProductId`, CN code or commodity differ from the current copy (so a supplier-only or operator-only refresh never causes it, while a different Product with the same CN code and commodity does), then `Pending`, `OutsideRegulatoryScope` (`FlowSupport` ignored), and for `InScope`: `Pending`, `UnsupportedFlow` (recorded, or the policy-v1 envelope rejects Wood/Cattle/Other, Export, a non-single-commodity flow or a non-Operator role) or `WithinSupportedScope`.
- **Recipients:** versioned statement, `RecipientsIdentified` (1-50 complete recipients) or `NotApplicable` (no recipients, recorded basis). No statement means unresolved and is never silently converted.
- **Evidence links record presence only.** A `CaseEvidenceLink` says a retained document of the *same case* is offered for a purpose (`Legality`, `DeforestationFree`, `Applicability`, `ProductionSource`). It does not mean reviewed, sufficient, compliant, deforestation-free or legal. Withdrawn (one-way, with actor), never deleted; one current link per (case, document, purpose). The same-case guarantee is database-enforced by a new `Documents (OrganizationId, EudrCaseId, Id)` alternate key and a composite FK.
- **Operator profile:** one per organization, mutable, deletion rejected. It is a *source* for the copy, never a case fact. EORI is stored, not evaluated, and not DDS readiness.
- **Persistence guards (application-level, like ADR 0005-0007):** `CaseMasterDataVersion`, `CaseApplicability` and `CaseRecipientStatement` join the `Retirement` map (`SupersededAtUtc`), `CaseEvidenceLink` too (`WithdrawnAtUtc` with `WithdrawnByUserId`), `CaseRecipient` is fully immutable, `OperatorProfile` deletes are rejected. Other save overloads, bulk writes and raw SQL bypass them; the Restrict FKs and unique indexes are the database backstop.
- **Working-fact write protocol:** transaction, case lock `FOR UPDATE` (404), `EnsureEditable` (409), body validation (400), then supersede, save and insert; identical normalized content is a 200 no-op without a version or audit event. Terminal (Completed/Archived) cases reject every write, including refresh. Audit text carries identifiers only.
- **Additive migration `CompletenessFacts`** with a `DO $$` Down guard that refuses once any new table has a row or any supplier has a postal address. No backfill and no fabrication: legacy cases have no copy, applicability, recipients or links.

Implemented in commit 2 (read model, no schema change):

- **Completeness is a pure read model of the current working dossier, computed on every `GET` and never stored.** `DossierFactsBuilder` collects the current case-owned facts and immutable rows (shipment, master-data copy, applicability, recipients, lot with pinned revisions, current documents/geolocation/submission, non-withdrawn evidence links, requirements) into `DossierFacts`; the live catalogue is read only to compute advisory drift. `CompletenessEvaluator` applies policy v1 (an explicit code-defined policy with a `Limitations` list; no rules engine, no stored rules, a rule change bumps the policy version). `CompletenessService` orchestrates it inside a repeatable-read snapshot and writes nothing.
- **Three separate axes, no combined verdict.** `dataCoverage` (`Complete | Incomplete`) is decided by the items of the MasterData, Applicability, Product, Quantity, Production and Parties groups only; `evidenceReadiness` (`EvidenceMissing | AwaitingRequirementDecisions | ReadyForOwnerReview`, deliberately no "Reviewed" value) by the Evidence group; `reviewFreshness` is `None` before the first review and `Current`/`Stale` afterwards. No value anywhere is named Compliant, LegallyCompliant, SafeToTrade or DeforestationFree (pinned by a unit test).
- **Item statuses** are `Satisfied | Missing | Invalid | AwaitingReview | NotApplicable`; `NotApplicable` needs a recorded basis and `AwaitingReview` is used only for a `Submitted` requirement. A requirement `Accepted` is a requirement-level decision, never a dossier review. Evidence links count as presence only and only while the link is not withdrawn **and** its document is current.
- **Canonical fingerprint (version 1).** SHA-256 (lower-case hex) over a compact UTF-8 JSON envelope of the *facts*: fixed property order, id-sorted collections, decimals by value, ISO dates, string enums. Section hashes: Shipment, MasterData, Applicability, Recipients, Lot, Requirements, Evidence. Master data is fingerprinted by fact-bearing content, not by version id; `ProductName`, `ProductCatalogueDescription`, producer/plot labels, active flags, `RevisionSupersededAtUtc`, case status, audit and live drift are excluded; requirement `ReviewedByUserId`/`ReviewedAtUtc` are facts; the geometry SHA-256 of each pinned revision is a fact. A change to the canonical form must add a fingerprint version and keep the old ones computable (a unit test pins a reference value).
- **Advisories** (`CATALOGUE_DRIFT_<AREA>`, `PINNED_REVISION_SUPERSEDED`) never make a case incomplete and never enter the fingerprint: a pinned plot revision superseded later does not change what the case adopted.
- The working export gains `completeness`, `latestReview` (null) and `reviewScope`; case status, `Complete` and the requirement PATCH are unchanged, so a case can be `ReadyForExport` or `Completed` while completeness says `Incomplete`.

Implemented in commit 3 (immutable reviewed history):

- **Hybrid snapshot.** A `CaseRevision` pins the immutable or case-owned rows the review relied on through case-consistent composite Restrict foreign keys (dossier and lot, applicability, recipient statement, master-data version, geolocation, supplier submission, plus `CaseRevisionDocument` and `CaseRevisionEvidenceLink` rows for the current documents and non-withdrawn links), and copies the values that can change later into the typed `SnapshotJson` (`CaseRevisionSnapshotV1 { schemaVersion, facts, context, completeness }`, explicit records, never EF entities). `facts` mirror the fingerprinted content; `context` freezes producer/plot labels, `ProductName`/`ProductCatalogueDescription`, whether each pinned revision was already superseded and the drift at review time; `completeness` stores the evaluation relied on (never the dynamic freshness or latest review). A stored review is read from its snapshot and pins, never recomputed under today's policy or the live catalogue.
- **`ReviewRecord`** is one-to-one with its revision (unique `CaseRevisionId`), with decision, a required rationale (max 4000), reviewer, `ReviewedAtUtc` and policy version; fully immutable. "Latest" is always the highest `CaseRevision.Number` (unique per case): `ReviewedAtUtc` may collide (non-unique index) and is never used to order.
- **Four decisions, no compliance verdict:** `AcceptedAsCompleteUnderPolicy` (shipment match satisfied, applicability `WithinSupportedScope`, no Missing/Invalid/AwaitingReview item, no catalogue drift; `NotApplicable` items are allowed; it means only "accepted as complete under the versioned Provena pilot completeness policy"), `ConfirmedOutsideRegulatoryScope` and `ConfirmedUnsupportedFlow` (shipment match satisfied and the matching derived applicability status; flow support may stay Pending outside scope; `OtherUnsupported` derives an unsupported flow) and `ReturnedForCorrection` (always allowed, even with a master-data mismatch). A failed positive precondition is 409 with structured `failingItems`. `ProductChanged` blocks all three positive decisions.
- **Owner gate.** `POST .../reviews` runs a live `OrganizationUsers` query (user + organization + role Owner) inside the transaction before any case lookup and before the body is read, so a Member gets 403 for an existing, nonexistent or foreign case and for an invalid body alike; the JWT role is never trusted. No new roles, membership API or RBAC framework; every other write keeps its member semantics.
- **Transaction order (a contract):** begin; Owner check (403); case lock `FOR UPDATE` (404); `EnsureEditable` (409); body validation (400); read the shipment; lock `OperatorProfile`, the shipment's `Supplier` and `Product` `FOR SHARE` (same order as the master-data refresh); build facts, evaluate, fingerprint, drift; resolve the latest review by `Number`; compare `expectedFingerprint` and `expectedLatestReviewId` (null means "no review existed", 409 `Dossier or review history changed since it was loaded`); decision preconditions (409); next `Number`; insert revision, pins and record; audit `CaseReviewRecorded` (ids and decision name only); bump `UpdatedAtUtc`; commit. Two simultaneous reviews of the same state therefore yield one 201 and one 409; a review racing a case write is serialized by the case lock, and a catalogue edit either waits on `FOR SHARE` or committed first and appears as drift.
- **Freshness (derived on read, never stored).** `Current` iff the current fingerprint computed with the review's stored `FingerprintVersion` equals the stored one; otherwise `Stale` with `changedAreas` (the sections whose hashes differ, in the order Shipment, MasterData, Applicability, Recipients, Lot, Requirements, Evidence). Old fingerprint versions stay executable forever; an unknown stored version is an error, never silently reinterpreted. `policyChanged` is informational and never stales a review. Not stale: catalogue edits without a refresh (drift advisory only), a context-only master-data refresh, producer/plot renames and active flags, a superseded pinned revision (`PINNED_REVISION_SUPERSEDED`; the review adopted that immutable revision, and a newer one is adopted only by a deliberate lot save, which does stale), case status, audit, exports and the supplier-request lifecycle. Stale: any shipment, lot, applicability, recipient, fact-bearing master-data, evidence or requirement change, including a same-status requirement re-review (the reviewer id and `ReviewedAtUtc` are facts).
- **Completed and Archived cases** accept no new review, refresh or enrichment (409) but keep their reviews, the reviewed export and the freshness readable; a review that was Current when the case was completed stays Current because every fingerprint input is case-owned or immutable. `Complete` is not gated by a review and there is no release status. *[Superseded in part by ADR 0009: `Complete` and the `Completed`/`Archived` statuses no longer exist; a Closed or archived case rejects the same writes, and a Current Owner review is now required to close.]*
- **Reviewed export.** `GET .../reviews/{reviewId}/export` is built only from the `CaseRevision` and the rows it pins: `review.json` (explicit DTO with the stored snapshot and a scope notice), `plots/{revisionId:N}.geojson` of the exact pinned revisions, the pinned documents even if withdrawn later, and the pinned geolocation original. It reads no live catalogue, rebuilds no working dossier and needs no case lock; the audit event `CaseReviewExported` carries ids only. The working export stays working-current and now carries the real `latestReview`.
- **Persistence.** Migration `ReviewedDossierHistory` is additive: four tables, eight case-consistency alternate keys (`CaseDossiers`, `CaseLots`, `Geolocations`, `Submissions`, `CaseApplicabilities`, `CaseRecipientStatements`, `CaseEvidenceLinks`, `CaseMasterDataVersions`) and Restrict foreign keys only, a unique `(EudrCaseId, Number)`, a unique `ReviewRecords(CaseRevisionId)` and a **non-unique** `ReviewRecords(EudrCaseId, ReviewedAtUtc)`. **CHECK-constraint exception:** `CK_CaseRevisions_DossierLotPair` (both `CaseDossierId` and `CaseLotId` null or both set) is the single deliberate structural CHECK in this schema, because a composite foreign key with MATCH SIMPLE skips the dossier -> lot check on a half-null pair; every value rule stays in validators, and "the pinned lot is the current lot" stays a `ReviewService` obligation. The four review tables are fully immutable and never deleted (`Review history is immutable; record a new review.`), an application-level guard like ADR 0005-0007. Down is guarded and refuses once any review-history row exists.

Deliberately undecided: risk assessment and mitigation, release/approval, DDS and EU Information System semantics, downstream/trader workflows, cattle establishments, wood species, composite products, Article 4a, split/merge, coordinate-precision evaluation, per-source evidence links, document hashing/WORM.

## Alternatives considered

- **Live catalogue reads for party and product facts.** Rejected: any member's catalogue edit would silently change a case's facts (and, later, a reviewed fingerprint) without a case lock or audit trail.
- **Freeze the facts when the case completes (B).** Rejected: needs a second frozen code path and still lets an unrelated shared-row edit act as an unreviewed change to an open case.
- **Fingerprint only case-owned data and ignore party facts (B').** Rejected: loses reproducibility of the facts a review relied on.
- **Assessed product facts read from the live `Product`.** Rejected: the assessment would drift with the catalogue; it is copied from the case's own master-data copy.
- **Product identity by CN code and commodity only.** Rejected: two products with the same CN code and commodity are different goods; `AssessedProductId` is part of the comparison.
- **Treating a document link as evidence sufficiency.** Rejected: sufficiency is a human legal judgement, not a stored per-document finding.

## Consequences

- A supplier or product referenced by any master-data copy or applicability can no longer be physically deleted (FK Restrict; surfaces as the generic 409 for a referenced record), even if a shipment no longer uses it.
- Existing-table changes are only `Suppliers.PostalAddress` (nullable, max 1000, optional trailing field of `SupplierInput`, CSV header unchanged) and the `Documents` alternate key. A supplier PUT that omits `postalAddress` clears it (complete-replacement semantics, as for the other optional supplier fields).
- Legacy cases keep working unchanged; applicability needs a master-data refresh first.
- Rollback of `CompletenessFacts` is possible only while the six tables are empty and no supplier has a postal address; rollback of `ReviewedDossierHistory` only while the four review tables are empty.
- A supplier, product, producer, plot, document or evidence link that a review pins can never be physically deleted (Restrict foreign keys), consistent with the append-only evidence rules.
- Reviews pin and copy retained party and location data (names, addresses, e-mails, plot geometry hashes and the pinned documents); retention and erasure of review history is part of the open legal item.
- No requirement status, case status or `Complete` eligibility changes; nothing here is a legal-compliance claim. *[Superseded in part by ADR 0009: closing now requires a Current Owner review; reviews still change no requirement status.]*
