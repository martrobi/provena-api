# EUDR domain as represented in Provena

This is a description of the supplied implementation and explicit project direction, not a regulatory interpretation. Evidence: `Domain/`, `Services/ShipmentService.cs`, `EudrCaseStatusService.cs`, `CaseService.cs`, `SupplierRequestService.cs`, `CaseFileService.cs`, `ExportService.cs` beneath `src/Provena.Api/`. Declared database constraints and application guard limits are documented in [DATABASE](DATABASE.md); migrations/tests have not been executed here.

## Concepts today

An Organization owns operational tenant data. A Supplier is a commercial counterparty. A Product contains a CN code as a string (preserving leading zeroes), commodity enum and active flag. A Shipment references one supplier and one product, one quantity/unit, origin and optional dates. No shipment-line collection exists. A new shipment creates one EudrCase and six required EudrRequirements, initially Missing:

| Requirement | What the current submission path treats as present |
| --- | --- |
| SupplierInformation | Any valid SaveDetails request marks it Submitted, even if all optional fields are empty |
| CountryOfProduction | Nonempty country code; validator checks two uppercase letters, not a country registry |
| ProductionPeriod | Both from/to dates; validator checks order when both are provided |
| QuantityConfirmation | Positive confirmed quantity (at most 6 decimals, otherwise 400); it is recorded even when it differs from the shipment quantity and is compared with it only by Quantity Reconciliation v1 (see below) |
| Geolocation | Accepted geometry file upload |
| SupportingDocuments | A document upload; category does not change the checklist type |

Evidence is retained, not overwritten ([ADR 0005](adr/0005-retained-evidence-append-only-rows.md)). _Withdrawn_ = a document removed from the current dossier by an internal user (row and bytes kept); _superseded_ = a geometry or supplier-details version replaced by a newer one. Exactly one geometry and one supplier-details row per case is _current_; workflows, review, export and the public portal see only current evidence. Version order is `CreatedAtUtc` then `Id`; there are no version numbers. Retained versions alone do not imply reviewer acceptance. Owner dossier reviews pin exact evidence versions and snapshot requirement decisions; there is no separate immutable history of every requirement-level decision. SupplierSubmission stores one case-level production country, period, quantity and notes per version (the current one is used). SupplierRequest grants token access to the case and tracks sent/opened/completed/revoked/expiry timestamps. CaseDocument stores metadata and a file key; GeoSubmission stores one current geometry file plus normalized JSON and structural validation summary. AuditEvent records workflow events.

## Exact status priority (observed)

`EudrCaseStatusService.Calculate` applies the following order; do not reorder as a cleanup. `CalculateOpen` is the same order without row 1 and never returns `Closed`; archive is not a status and does not appear here:

| Priority | Condition | Result |
| --- | --- | --- |
| 1 | Current state Closed | Preserve Closed (left only by an explicit Owner reopen) |
| 2 | No request with non-null SentAtUtc | Draft |
| 3 | Any required requirement Missing | WaitingForSupplier |
| 4 | Any requirement Submitted or Rejected (including optional) | ReviewNeeded |
| 5 | All required requirements Accepted or NotRequired | ReadyForExport |
| 6 | Otherwise | WaitingForSupplier |

Request-sent means **any historical request** with SentAtUtc; revoked/expired requests still count. The timestamp is set at creation even with the email stub. No supplier-completion timestamp is needed for readiness. With a sent request, all six requirements could be waived and yield ReadyForExport.

Reviewer input allows Accepted, Rejected or NotRequired. Accept/reject requires current Submitted; NotRequired bypasses that precondition and does not require a nonempty note. A new/changed piece of evidence clears review metadata and sets its requirement to Submitted or Missing, except NotRequired stays unchanged. Details updates reset four requirements together, even if values did not change. Document upload/withdrawal (DELETE) resets SupportingDocuments (Missing when no current document remains, otherwise Submitted); geometry upload resets Geolocation. Resubmitting after review keeps the earlier values as a superseded version, but the live requirement's review decision (note/reviewer/time) is still cleared; a prior Owner review retains its snapshot of that decision, while changes between Owner reviews have no independent immutable decision history. A resubmitted details save also clears supplier completion, so the case returns to waiting for the supplier.

Supplier completion rejects required Missing/Rejected items, sets timestamps and recalculates status; it does **not** accept requirements or lock further supplier edits. Public writes clear completion timestamps for that request/case. Repeated supplier completion can add repeated audit events. There is no internal "complete" action any more: closing is the Owner-backed lifecycle action described under "Case lifecycle v2".

`CaseService.EnsureMutable` rejects business writes on a Closed case (409 "Closed cases cannot be changed; reopen the case first.") and on an archived case (409 "Archived cases cannot be changed; unarchive the case first."), including the public GET through LockPublic. Exceptions to blanket immutability: supplier-request revoke still operates; export remains allowed in every state and adds an audit event; a Closed case can be archived; catalog edits can change supplier/product data that an old case displays or exports from the live catalogue (case-owned master data, reviewed exports and the review snapshot do not drift). Do not describe a closed case as a frozen copy of the catalogue.

Shipment updates are blocked once any supplier request exists, evidence has a status other than Missing/NotRequired, or the case has a dossier (any saved lot; 409, checked under the case lock; creation is unchanged). Shipment archival no longer exists: archive is a case-level lifecycle action. Internal document withdrawal does not explicitly clear supplier-completion timestamps. These are observations to review, not new endorsed business rules.

## Geometry boundaries

The validator supports Polygon/MultiPolygon directly or wrapped in Feature/FeatureCollection. It checks nonempty geometry, finite coordinates, longitude/latitude ranges, closed rings and topology with NetTopologySuite; Feature properties must be object/null. Point geometries are rejected for case uploads (plot geometry has its own validator, see below). A third coordinate is allowed and checked for finiteness but topology uses only the first two. FeatureCount counts geometry objects processed, not individual polygons inside a MultiPolygon and not production plots.

Invalid uploads return 400 rather than saving an Invalid GeoSubmission. Valid geometry means structural/topological validity only. It does not prove location authenticity, land ownership, production attribution, deforestation status or regulatory sufficiency.

## Explicit target decision: separate counterparties and production

[ADR 0002](adr/0002-supplier-producer-production-plot.md) records **Supplier != Producer != ProductionPlot**. A supplier may be an exporter, cooperative or intermediary; a producer may have multiple plots. Implemented (persistence model and internal authenticated API, see [API](API.md); no public routes, see [ADR 0006](adr/0006-production-provenance-plot-revisions.md)): `Producer`, `ProductionPlot` and `PlotRevision`. The case dossier / lot-source model and its internal API are implemented (see the next section, [ADR 0007](adr/0007-case-dossier-lot-attribution.md)). Supplier/producer relationships are **not** implemented. Do not rename GeoSubmission to ProductionPlot, assume one uploaded feature is one plot, or infer Supplier == Producer. Ownership, duplicate identity across producers and any backfill of existing case geometry remain undecided; existing `GeoSubmission` evidence is untouched.

- **Producer:** stable tenant-owned identity (name, optional external reference, optional own country, notes, `IsActive`). Never deleted; deactivated. Descriptive edits overwrite values (no producer history).
- **ProductionPlot:** a stable **producer-scoped plot registration**, not a canonical identity of the physical parcel. Each plot belongs to exactly one producer and `ProducerId` is immutable; a producer or tenure change is a new plot (shared or multi-producer plots are deferred, with no guarantee that adding them is non-breaking). It holds no location data. Never deleted; deactivated.
- **PlotRevision:** immutable material location data (country of production, geometry type Point/Polygon/MultiPolygon, normalized geometry JSON, optional declared `AreaHectares`, note). Exactly one revision is current (`SupersededAtUtc IS NULL`); older revisions stay retrievable and remain valid targets for later references. Only a *material* change creates a revision: geometry, country or declared area. A change that is not material is rejected by `ProvenanceService` with 409 as a no-op; the comparison is `GeoJsonValidationService.IsMaterialChange` — geometry by NetTopologySuite topological equality (ring start, orientation, MultiPolygon component order and a single-component MultiPolygon vs the identical Polygon are not changes), country by exact value, declared area by exact decimal value. The revision note alone is never material.
- **Active semantics (enforced in `ProvenanceService` under row locks, not by the schema):** a plot can only be created for an active producer (decided on the locked producer row); a revision can only be created for an active plot (decided on the locked plot row; the producer's activity is not checked); deactivating a plot does not supersede its current revision.
- **Plot geometry validation:** `GeoJsonValidationService.ValidatePlotGeometry` accepts one bare Point, Polygon or MultiPolygon geometry object (no Feature/FeatureCollection) with the same range/closure/topology checks as case uploads, a 5 MiB size cap, and no vertex limit. **Valid plot geometry means structural validity only**, not EUDR completeness or sufficiency of the geolocation (no 4 ha point/polygon rule, no precision rule). Case uploads (`Validate`) still reject Point.

## Case dossier and lot sources

Implemented as a persistence model plus the internal authenticated API ([API](API.md): `GET dossier`, `PUT dossier/lot`, `GET dossier/lot-history`). Recorded facts only: this is not applicability, Article 9 completeness, risk assessment or a DDS ([ADR 0007](adr/0007-case-dossier-lot-attribution.md)).

- **CaseDossier:** the stable case-owned anchor representing the case's one physical lot. At most one per case; fully immutable; never deleted. It holds no business facts. Multi-lot cases, lot transfer, split, merge and processing/conversion are unsupported.
- **CaseLot:** an immutable version of the facts about that lot (sequential `Number`, `LotReference`, `Quantity` `numeric(20,6)`, `Unit`, optional note). Exactly one version is current; saving new facts will supersede it. **`LotReference` is a versioned operator business/batch reference, not a permanent lot identity:** it is unique among *current* lots in an organization, a superseded reference may be reused, and the dossier (not the reference) is what ties the physical lot to its case.
- **LotContribution:** one producer's quantity in one lot version, in the lot's unit. No supplier is recorded or inferred; Supplier == Producer is never assumed.
- **ContributionPlot:** attributes a contribution to one plot at one **pinned** `PlotRevision`, so later plot edits cannot rewrite what a lot version used. No per-plot quantity. The database enforces that the revision belongs to the plot, the plot belongs to the producer, and that producer is the contribution's producer (composite FKs). Optional `ProductionStartDate`/`ProductionEndDate`: both or neither, start <= end (API validator rules, not SQL). These dates are factual source data; they are not a completeness or legal-sufficiency claim and are not compared with the EUDR cut-off date or plot revision dates.
- **Quantity semantics (enforced by `CaseDossierService`):** a contribution is the portion of the lot's own material from that producer in the lot's unit; reconciliation is derived on read by exact decimal equality; same unit only, no conversion, no tolerance, over-allocation rejected, under-allocation storable. This contributions-to-lot rule is unchanged; the lot is additionally compared with the shipment and the supplier-confirmed quantity by the completeness policy (next sections, [ADR 0010](adr/0010-quantity-reconciliation-v1.md)).
- **Active / carry-over (API rule, under row locks, not by the schema):** new attribution (a producer, a plot, or a different pinned revision relative to the current lot version) requires an active producer and an active plot (409); sources carried over from the current version stay usable after deactivation and may have their quantity or production period corrected. A superseded revision may be pinned; the exact submitted revision is never replaced by "current".
- **Lifecycle:** a lot may be saved while the case is Draft, WaitingForSupplier, ReviewNeeded or ReadyForExport; Closed and archived cases reject saves (409) but remain readable and exportable. Saving never changes requirements or the case status. Once a dossier exists the shipment is no longer editable (409). The export carries the current lot and its pinned geometries as a working snapshot, not a reviewed one.
- **Not implemented:** risk, release and DDS (the working facts, completeness and reviewed history are in the next sections), multi-lot cases, unit conversion, per-plot quantities and tolerance. `GeoSubmission` is never converted into lot sources.

## Completeness facts: operator, case master data, applicability, recipients, evidence links

Implemented as working facts plus the internal authenticated API ([API](API.md)); the completeness read model and the immutable reviewed history are described in the next sections ([ADR 0008](adr/0008-completeness-facts-and-reviewed-history.md)). These records state what was entered or assessed. Nothing here is a legal-compliance, sufficiency, risk, release or DDS claim, and none of it changes requirement statuses, the case status or `Complete` eligibility.

- **OperatorProfile:** the organization's own legal name, postal address, e-mail, establishment country and optional EORI. One per organization, mutable, never deleted. It is only a **source** for the case copy below. EORI is stored; it is not evaluated and is not DDS readiness.
- **Case master data (`CaseMasterDataVersion`):** the case-owned copy of the operator, supplier (name, postal address, e-mail, country) and product (CN code, commodity, plus name and catalogue description as context only) values a case relies on. Immutable and versioned; a member runs an explicit refresh to adopt current catalogue values (new version, audit `CaseMasterDataRefreshed`). Identical values are a no-op. Shared catalogue edits never change the copy.
- **Shipment binding:** the copy's `SupplierId`/`ProductId` come from the case's current shipment under the case lock. A shipment may change supplier/product until it is locked (supplier request, evidence progress or a dossier); the copy then no longer matches (`shipmentMatch: false`), applicability cannot be saved (409) and a refresh adopts the shipment's current supplier and product.
- **Catalogue drift** is advisory: the live operator profile and the copy's own supplier and product are compared with the copy over fact-bearing fields only (not product name or catalogue description, not timestamps). It never changes the case. Acceptance as complete under the policy requires an explicit master-data refresh when fact-bearing catalogue drift exists; see ReviewPreconditions and the Owner review section below.
- **Applicability (`CaseApplicability`):** a human's recorded assessment, versioned and immutable. The assessed product (`AssessedProductId`, CN code, commodity) is copied by the server from the matching master-data copy. `ProductDescription` is the **authoritative assessed trade description** for the case; the catalogue `Product.Description` is reusable default text and context only. `OperatorRole` is `Operator` or `OtherUnsupported` (description required, always an unsupported flow). A decided scope (`InScope`/`OutsideRegulatoryScope`) needs citation, legal-basis version, effective date, activity date and reasoning; `InScope` also needs the product description. Anyone in the organization may record it (the decider is stamped); no owner confirmation exists yet.
- **Derived applicability status** (never stored; `ApplicabilityDerivation`): `NotRecorded`; `ProductChanged` (assessed product id, CN code or commodity differ from the current copy; a supplier-only or operator-only refresh does not cause it, a different product with the same CN code and commodity does); `Pending`; `OutsideRegulatoryScope` (flow support ignored); for `InScope`: `Pending`, `UnsupportedFlow` or `WithinSupportedScope`. Pilot policy flow envelope (introduced in policy v1, unchanged in v2): Coffee, Cocoa, Rubber, Soy and OilPalm placed on the market by import or domestically as the Operator for a single relevant commodity are supported; Wood, Cattle, Other, Export, non-single-commodity flows and `OtherUnsupported` are `UnsupportedFlow`. CN code format never implies applicability and there is no tariff or Annex I engine.
- **Recipients:** `RecipientsIdentified` (1-50 recipients, every field required) or `NotApplicable` (no recipients, recorded basis). No statement is **unresolved**, which is not the same as `NotApplicable`.
- **Evidence links:** "this retained document of this case is offered for this purpose" (`Legality`, `DeforestationFree`, `Applicability`, `ProductionSource`). A link is **presence only**: not reviewed, not sufficient, not legal, not compliant, not deforestation-free. Withdrawn, never deleted. The link list keeps withdrawn links (with `withdrawnAtUtc`); a link whose document was withdrawn later stays listed with the document's withdrawal visible as a separate fact. Only non-withdrawn links to non-withdrawn documents are current.
- **Lifecycle:** all of these are written while the case is Draft, WaitingForSupplier, ReviewNeeded or ReadyForExport; Closed and archived cases reject every write including a master-data refresh (409) but remain readable. Legacy cases have no copy, applicability, recipients or links; nothing is backfilled.

## Completeness policy (v2), the three axes and the fingerprint

Implemented as a read model ([API](API.md) "Completeness", [ADR 0008](adr/0008-completeness-facts-and-reviewed-history.md)); review records, the Owner gate and freshness against stored reviews are described in "Immutable reviewed history". Completeness answers one question only: do the *recorded facts* of the current working dossier satisfy the checks of a versioned pilot policy? It is not legal compliance, a risk assessment, a deforestation-free finding, a sufficiency judgement of any document, or DDS readiness.

- **Policy** `provena-pilot-completeness` version `2` (it was `1` until Quantity Reconciliation v1, [ADR 0010](adr/0010-quantity-reconciliation-v1.md)), defined in code (`CompletenessPolicy`, `CompletenessEvaluator`) with an explicit limitations list: coordinate precision is not evaluated; legality and deforestation-free sufficiency is human judgement; EORI is stored but not evaluated; no unit conversion or tolerance, with the quantity rules of the single-lot pilot assumption below; unsupported flows stay unsupported; production periods are checked for presence only; a CN code is checked for format only; an `Accepted` requirement is not a dossier review. Changing a rule means changing code and bumping the policy version; there is no rules engine and no stored rule definition.
- **Axis 1, `dataCoverage`:** `Complete` only if no item of the MasterData, Applicability, Product, Quantity, Production and Parties groups is `Missing` or `Invalid`. Evidence items never decide it. **Axis 2, `evidenceReadiness`:** `EvidenceMissing` (any Evidence item `Missing`/`Invalid`), else `AwaitingRequirementDecisions` (a `Submitted` requirement), else `ReadyForOwnerReview`; there is deliberately no "Reviewed" value, and decided requirements plus linked documents can at most make evidence ready for an Owner. **Axis 3, `reviewFreshness`:** `None` before the first review, then `Current` or `Stale` for the latest human review; a reviewed state exists only as the latest review decision together with this freshness.
- **Pilot owner defaults applied (D1-D7):** unsupported flows (Wood, Cattle, Other, Export, non-single-commodity, `OtherUnsupported` role) are `Invalid` on `FLOW_SUPPORTED`; a Point needs a declared area of at most 4 ha (polygon area is never computed); both production dates are required for every pinned source; recipients must be identified or `NotApplicable` with a basis (unresolved is `Missing`); legality and deforestation-free evidence need at least one non-withdrawn link to a current document, as presence only.
- **Shipment binding** is itself an item: `MASTER_DATA_SHIPMENT_MATCH` is `Invalid` when the case copy no longer describes the shipment's current supplier or product, and `Missing` without a copy. Nothing refreshes automatically.
- **Fingerprint (version 1)** identifies the *facts*: shipment (reference, supplier and product ids, quantity, unit, origin, dates); master-data **content** (operator fields, supplier id and fields, product id, CN code, commodity - not the version id); the current applicability (id and every field incl. `AssessedProductId`, role and role description, decision stamp); the recipient statement and entries; the lot (id, number, reference, quantity, unit, note, reconciliation, contributions by producer id and quantity/unit, plot links by plot id and **exact pinned revision id** with revision number, country, geometry type, declared area, SHA-256 of the geometry and the production period); current documents, geolocation and supplier submission with their facts and the non-withdrawn evidence links; requirements (type, `IsRequired`, status, note, `ReviewedByUserId`, `ReviewedAtUtc`). Quantity Reconciliation v1 did not change this canonical form (every compared quantity was already a fact). **Excluded:** `ProductName` and `ProductCatalogueDescription` (context), the master-data version id, producer/plot names and active flags, `RevisionSupersededAtUtc`, case status, audit events, export timestamps and live catalogue drift. Per-section hashes (Shipment, MasterData, Applicability, Recipients, Lot, Requirements, Evidence) use the same canonical form (invariant decimals without trailing zeros, ISO dates, UTC timestamps, string enums, id-sorted collections, lower-case SHA-256 hex).
- **Advisories, not failures:** catalogue drift (`CATALOGUE_DRIFT_*`) and a pinned plot revision that has since been superseded (`PINNED_REVISION_SUPERSEDED`: the case adopted that immutable revision; moving to a newer one needs a deliberate lot save). They do not make a case incomplete and are not part of the fingerprint.
- **Independent of the operational lifecycle:** `EudrCaseStatus`, the requirement PATCH and the dashboard are unchanged by completeness; a case may be `ReadyForExport` or `Closed` while completeness reports `Incomplete` (an `OutsideRegulatoryScope` or `UnsupportedFlow` closure does not need the in-scope completeness set). Closing is gated by a Current Owner review, not by completeness directly.

### Quantity Reconciliation v1 (completeness policy v2)

Implemented ([API](API.md) "Completeness", [ADR 0010](adr/0010-quantity-reconciliation-v1.md); handoff [quantity reconciliation](frontend-handoffs/2026-10-quantity-reconciliation.md)). A pure, derived comparison of the quantities recorded for a case (`Services/QuantityReconciliation.cs`). It states whether the *recorded* quantities agree; it is not a legal net-mass, compliance or DDS-readiness finding.

- **Pilot single-lot assumption.** One shipment/case is represented by exactly one current `CaseLot` (ADR 0007). The direct rule Shipment == current CaseLot holds only under that assumption and is not a permanent rule; a multi-lot or split model needs a different aggregate rule, its own policy version and an ADR. Out of scope.
- **Rules.** Exact decimal equality in one unit (`10` equals `10.000000`); no unit conversion (10 Ton is neither 10 nor 10000 Kg); no tolerance; derived on every read, never stored, never manually overridden. Three checks in a fixed order: `SHIPMENT_LOT` (shipment vs current lot), `SUPPLIER_CONFIRMED_SHIPMENT` (confirmed quantity vs shipment) and `CONTRIBUTIONS_LOT` (sum of producer contributions vs lot).
- **Statuses and outcome.** Check status `Matched | MissingData | UnitMismatch | QuantityMismatch | NotApplicable`; outcome `UnitMismatch` > `QuantityMismatch` > `MissingData` > `Matched`; `NotApplicable` checks never count. A shipment in unit `Other` can never match a lot (a lot is never `Other`).
- **Supplier-confirmed quantity.** It has no unit of its own and is taken to be in the shipment's unit (`unitImplied`), so that check can never be a `UnitMismatch`. **Every existing confirmed quantity is compared** with the shipment, whatever the `QuantityConfirmation` requirement says. When none exists the check mirrors the `REQUIREMENT_QuantityConfirmation` item and does **not** consult `IsRequired` (that shortcut was removed): `NotRequired` with a nonblank reviewer note (the recorded basis) is `NotApplicable`; `NotRequired` without one is `MissingData` (field `quantityConfirmationWaiverBasis`); any other state is `MissingData` (field `supplierConfirmedQuantity`). Hence the reconciliation is never `Matched` while that requirement item is `Missing` for an unbacked waiver.
- **Supplier submission is not acceptance.** A confirmed quantity that differs from the shipment is accepted (204) and judged afterwards. The only public validation added is at most 6 decimals (400 otherwise), so an exact value is never silently rounded in storage.
- **Completeness items** (group `Quantity`, in order): `LOT_PRESENT`, `SHIPMENT_LOT_QUANTITY_MATCH`, `SUPPLIER_CONFIRMED_QUANTITY_MATCH`, `LOT_RECONCILED`. `MissingData` -> `Missing`, `UnitMismatch`/`QuantityMismatch` -> `Invalid`, `NotApplicable` -> `NotApplicable`, `Matched` -> `Satisfied`. Any `Missing`/`Invalid` makes `dataCoverage` `Incomplete`. `LOT_RECONCILED` with a non-zero under- or over-allocation is now `Invalid` (it was `Missing`); with no contributions it stays `Missing`.
- **Review gates.** A non-matched result blocks `AcceptedAsCompleteUnderPolicy` through the existing blocking-item rule; `ConfirmedOutsideRegulatoryScope`, `ConfirmedUnsupportedFlow` and `ReturnedForCorrection` have no quantity gate.
- **Close gate.** Closing as `ExternalDdsCompleted` also requires the current outcome to be `Matched`, evaluated under the case lock after the stale-review check, including for a Current review made under policy v1 (a policy-version change never stales a review). Failure: 409 ProblemDetails with `errors.reason = "QuantityNotReconciled"` and `errors.quantityReconciliation`; nothing is written. The other outcomes have no quantity gate; success is still 201.
- **Fingerprint and snapshot unchanged.** Every input is already a fingerprinted fact, so `FingerprintVersion` stays 1 and the review snapshot schema stays 1. Compatibility was verified against baseline commit `547f327` (see ADR 0010); a policy-version bump alone only sets `policyChanged`.
- **Not modeled:** legal net-mass and supplementary-unit semantics, unit conversion, tolerance, a stored confirmed-quantity unit, per-plot quantities, and any multi-lot, split or period-of-supply aggregate rule. A wrong shipment quantity cannot be edited once the shipment is locked; reconciliation can only be reached by changing the lot or the confirmed quantity.

## Immutable reviewed history

Implemented ([API](API.md) "Reviews", [ADR 0008](adr/0008-completeness-facts-and-reviewed-history.md)). A **review** is an accountable human's decision, recorded as an immutable `CaseRevision` (what was reviewed) plus a one-to-one `ReviewRecord` (the decision). It records that a person looked at exactly these facts under exactly this policy version and decided; it is **not** a legal-compliance determination, a risk assessment, a release or DDS readiness, and a review by itself changes no requirement and no case status. A Current review is, however, the gate for closing the case (see "Case lifecycle v2").

- **Who:** only an organization **Owner**, checked live against `OrganizationUsers` (not the token) before the case is looked up or the body is read, so a Member learns nothing about a case. Every other write keeps its member semantics. Reading reviews and the reviewed export is open to any member.
- **Decisions and their meaning:** `AcceptedAsCompleteUnderPolicy` = the facts are complete under the versioned Provena pilot completeness policy (shipment match satisfied, applicability within the supported scope, no Missing/Invalid/AwaitingReview item, no unadopted catalogue drift; `NotApplicable` items are fine). `ConfirmedOutsideRegulatoryScope` = the recorded applicability places the case outside the regulatory scope (flow support may stay Pending). `ConfirmedUnsupportedFlow` = the recorded flow is outside the pilot's supported envelope (including the `OtherUnsupported` role). `ReturnedForCorrection` = the Owner sends the dossier back; always allowed, even with a mismatch. The three positive decisions need a satisfied `MASTER_DATA_SHIPMENT_MATCH`; `ProductChanged` blocks them.
- **The Owner reviews what they loaded:** the request names the `fingerprint` and the latest review id the Owner saw; if either changed, the review is refused (409) and nothing is recorded. The case is locked and the live catalogue sources are locked `FOR SHARE` while that is decided, so there is no torn view.
- **What is stored:** pinned immutable rows (applicability, recipients, master-data copy, lot and dossier, geolocation, supplier submission, the current documents and non-withdrawn evidence links) plus a typed snapshot of the facts, frozen context (labels, product name/description, whether a pinned revision was already superseded, drift) and the completeness evaluation relied on. A later catalogue or label change, a superseded plot revision or a withdrawn document never rewrites it.
- **Freshness of the latest review (derived, not stored):** `Current` while the current facts fingerprint (computed with the review's stored fingerprint version) equals the reviewed one; otherwise `Stale` with the changed sections. Stale: shipment, master-data **content**, applicability, recipients, lot (including the pinned revision ids and production periods), evidence or requirement changes - including a same-status requirement re-review, because the reviewer and review time are facts. Not stale: catalogue edits without a refresh (drift advisory), a context-only master-data refresh, producer/plot renames and active flags, a pinned revision superseded later (advisory `PINNED_REVISION_SUPERSEDED`; adopting a newer revision needs a lot save, which does stale), case status, audit, exports, the supplier-request lifecycle and a policy-version change (`policyChanged` only).
- **Before and after Closed/archived:** while the case is mutable, reviews, refreshes and enrichment are allowed; once it is Closed or archived they are all refused (409), but existing reviews, their export and the freshness stay readable. A review that was Current when the case was closed stays Current (every input is case-owned or immutable, and lifecycle state is not part of the fingerprint). A Current review is what the Owner later closes the case on ([ADR 0009](adr/0009-case-lifecycle-v2.md)).
- **Not modeled:** more than the four decisions, per-document sufficiency findings, release/approval, risk, mitigation, DDS and EU Information System semantics, and membership management. Retention and erasure of review history is part of the open legal item.

## Case lifecycle v2: closing, reopening and archive

Implemented ([API](API.md) "Case lifecycle", [ADR 0009](adr/0009-case-lifecycle-v2.md)). ADR 0009 supersedes [ADR 0008](adr/0008-completeness-facts-and-reviewed-history.md) only where ADR 0008 says that Owner reviews do not gate completion/closure. Nothing here is a legal-compliance, risk, release or DDS-submission decision.

- **Two independent dimensions.** The *workflow status* is `Draft`, `WaitingForSupplier`, `ReviewNeeded`, `ReadyForExport` or `Closed` (stored as integers 0-4). `Completed` and `Archived` no longer exist. *Archive* is a separate, reversible dimension (a `CaseArchival` period) and never rewrites the workflow status.
- **`ReadyForExport` is an operational hint.** It is derived by `CalculateOpen` from sent requests and the six legacy requirement decisions only. It is not the closure gate: a `Draft` case with a Current Owner review can be closed, and a `ReadyForExport` case cannot be closed without one.
- **Closing (`CaseClosure`, Owner-only).** The Owner names `expectedReviewId`, which must be the **latest** review (highest `CaseRevision.Number`), the review must be **Current** for the present dossier (fingerprint freshness under the review's stored fingerprint version) and it must not already back a closure (**one review backs at most one closure**, also a unique index). The **outcome is derived from the review decision**, never chosen: `AcceptedAsCompleteUnderPolicy` -> `ExternalDdsCompleted`, `ConfirmedOutsideRegulatoryScope` -> `OutsideRegulatoryScope`, `ConfirmedUnsupportedFlow` -> `UnsupportedFlow`; `ReturnedForCorrection` **cannot close**. `ExternalDdsCompleted` **requires an external DDS reference** (trimmed, at most 200 characters, stored on the closure and not verified); the other two outcomes **reject** a reference. A stale review cannot close; only a new review of the changed dossier can. **Quantity gate ([ADR 0010](adr/0010-quantity-reconciliation-v1.md)):** closing as `ExternalDdsCompleted` also needs the current quantity reconciliation to be `Matched` (409 `QuantityNotReconciled`), also for a Current review made under policy v1; the other outcomes have no quantity gate.
- **Effects of closing.** The status becomes `Closed`, active supplier requests are revoked, one `CaseClosed` audit event (identifiers and outcome only, never the reference) is written. No requirement, review, fact or export is changed. A `Closed` case is immutable until explicitly reopened.
- **Reopening (`CaseReopening`, Owner-only).** The Owner names the current closure (`expectedClosureId`) and gives a non-blank reason. The workflow status is re-derived (`CalculateOpen`), a `CaseReopened` audit event is written, and **all** history is preserved: closures, reviews, exports, DDS references and audit events. Revoked supplier links are not restored. The old review already backs a closure, so closing again needs a **new** review even when nothing changed. A closure is reopened at most once; each new closure is the next `Number`.
- **Archive and unarchive (`CaseArchival`, Owner-only).** Both need a non-blank reason. Archive works in any workflow state (including `Closed`), leaves the status untouched, revokes active supplier requests and writes `CaseArchived`; unarchive retires the current period one way, restores nothing and writes `CaseUnarchived`. An archived case rejects **all** business mutations including close and reopen. Each period (with both reasons) stays as history; a later archive is the next `Number`.
- **Blocked while Closed or archived (409).** Requirement review, supplier-request create/regenerate, every public token route, internal document and geometry upload and withdrawal, lot save, master-data refresh, applicability, recipients, evidence-link create/withdraw, review creation, shipment edit; close again (Closed), archive again and close/reopen (archived). **Still allowed:** all reads, the working export, the reviewed export, supplier-request revoke (it only reduces access), archiving a Closed case, reopening a Closed case that is not archived, unarchiving.
- **History is reconstructable.** `CaseClosure` (immutable, backed by one `ReviewRecord`, carries the outcome and its own DDS reference), `CaseReopening` (immutable, one per closure, carries the reason) and `CaseArchival` (retire-only) are never deleted. `GET .../lifecycle` and the working export manifest (`lifecycle`) expose them. "Closed" means the highest-`Number` closure has no reopening; that is a service invariant, not a database constraint. Lifecycle state is not part of the dossier fingerprint, so these transitions never stale a review and `FingerprintVersion` did not change.
- **Lists and counts.** The case list excludes archived cases by default (`archived=exclude|only|include`). The dashboard has three mutually exclusive buckets: `activeOpen` (not archived, an open status), `activeClosed` (not archived, `Closed`, broken down by outcome) and `archived` (any status); `total` is their sum.
- **Removed.** `CompletedAtUtc` and the case-level `ExternalDdsReference` (the reference now lives on the closure), `POST .../complete` and `DELETE /api/shipments/{id}`. Local pre-v2 data was converted by migration `CaseLifecycleV2` (see [DATABASE](DATABASE.md)): no closure is invented for a legacy completion, because no qualifying Owner review ever existed.
- **Not modeled.** DDS verification or submission, a release/approval status, post-closure corrective action, Member archive rights, retention or erasure of lifecycle history.

## Responsibility boundary (project rule)

| Actor | Responsibility | Must not be inferred |
| --- | --- | --- |
| Supplier | Provide evidence and attest submission completion | Acceptance or compliance |
| Internal operator/reviewer | Decide requirement acceptance/rejection/waiver | Formal legal verification merely from authentication |
| Organization Owner | Records the immutable dossier review (accepted as complete under the pilot completeness policy, confirmed outside scope, confirmed unsupported flow, or returned for correction); closes a case on a Current review, reopens it with a reason, archives and unarchives it | A legal compliance, risk, release or DDS decision; closing is not a DDS submission and an external DDS reference is recorded, not verified |
| Provena automation | Format/geometry checks, checklist calculation, operational packaging | Regulatory risk assessment or legality |
| Regulatory/external process | Outside this implementation; optional reference recorded | Successful DDS submission or official approval |

Pending owner decisions include waiver justification/permissions; whether supplier completion should gate closing (a Current Owner review already does, see "Case lifecycle v2"); whether a Member may ever archive; verification or submission of a DDS reference; post-closure corrective action; retention period, disposal and erasure; deduplication of identical supplier-details saves; the policy for incomplete/archived working exports; legal net-mass and conversion semantics beyond the single-lot pilot reconciliation; and future multi-lot or supplier–producer relationships. Dossier completeness, case-owned catalogue copies, immutable Owner reviews and reviewed exports are already implemented as described above. An independent immutable history of every requirement-level decision is not implemented. No legal deadline, country-risk list or mandatory regulatory data rule is invented in this foundation.

## Engineering invariants for domain changes

Supplier, Producer and ProductionPlot are distinct concepts, not interchangeable entities ([ADR 0002](adr/0002-supplier-producer-production-plot.md), [ADR 0006](adr/0006-production-provenance-plot-revisions.md)). Producer, ProductionPlot and PlotRevision exist as an internal persistence model. Never infer Supplier == Producer or convert `GeoSubmission` into plots or lot sources. Case lot attribution ([ADR 0007](adr/0007-case-dossier-lot-attribution.md)) is implemented as a model plus the internal API (`CaseDossierService`, routes under `/api/eudr-cases/{caseId}/dossier`): `CaseDossier` is the stable case-owned anchor of the one physical lot, `CaseLot` rows are immutable versions (superseded, read through `Current()`), and `LotReference` is a versioned business reference unique only among current lots in an organization, not a permanent lot identity. Dossiers, contributions and plot links are fully immutable and never deleted; a link pins an exact `PlotRevision` id. New attribution (a producer, plot or different pinned revision relative to the current lot version) needs an active producer and plot, while carried-over sources stay usable; the route case is resolved and locked before the PUT body is validated; a shipment is not editable once its case has a dossier. Saving a lot never changes requirements or the case status, and nothing in it is a completeness or compliance decision. A plot belongs to one producer (immutable); a location change creates a new immutable `PlotRevision`, read through `Current()`. Producers, plots and revisions are never physically deleted; deactivate or supersede them. Ask the owner about new relationships, legal interpretations, review permissions, retention or changed status semantics before implementing those decisions. Continue unrelated unambiguous work.
Completeness is not compliance ([ADR 0008](adr/0008-completeness-facts-and-reviewed-history.md)). Case facts come from case-owned records, not the live catalogue: the master-data copy (`CaseMasterDataVersion`) changes only through an explicit, audited refresh on an editable case; catalogue edits are advisory drift. `GET completeness` is a pure read model under a versioned policy (three separate axes; never a combined verdict or a `Compliant`-style value); the fingerprint covers facts only, and any change to its canonical form needs a new `FingerprintVersion` with the old ones kept executable. A review (`CaseRevision` + `ReviewRecord`) is an immutable, Owner-only decision recorded by `ReviewService.Create` in its fixed order (live Owner check before any case lookup or body parsing, case lock, `FOR SHARE` catalogue locks, optimistic `expectedFingerprint`/`expectedLatestReviewId`); never edit, delete or re-derive a stored review, never decide "latest" by timestamp (use the revision number), never read the live catalogue for a stored review or reviewed export, and a stale review is only superseded by a new review. A document link is presence only, not review or sufficiency; a pinned plot revision superseded later is an advisory, not staleness. Reviews add no release status and are not legal, risk or DDS decisions. A Current Owner review is the only closure gate ([ADR 0009](adr/0009-case-lifecycle-v2.md)): lifecycle state is outside the fingerprint, so closing, reopening and archiving never stale a review; one review backs at most one closure; closure and reopening rows are immutable; never reintroduce `Completed`/`Archived` statuses, `CompletedAtUtc` or a case-level DDS reference.
