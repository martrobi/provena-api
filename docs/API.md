# API contracts

Authoritative source: the Minimal API modules in `src/Provena.Api/Endpoints/` (registered by `MapProvenaEndpoints()`, see [ADR 0003](adr/0003-minimal-api-http-layer.md)), `Contracts/Requests.cs`, `Contracts/Validators.cs` and the corresponding service. No versioned path prefix exists. OpenAPI says v1 but routes use `/api/...` or `/public/...`. OpenAPI/Scalar are available only in Development/Testing (`/openapi/v1.json`, `/scalar`). `HttpContractTests` checks that the document lists every route. Operation IDs and schemas are not treated as a contract.

Every internal route nests under the `/api` route group, which requires authorization. Only register and login opt out with AllowAnonymous. Public supplier endpoints form a separate group that is anonymous at the JWT level; services validate the secret capability. There is no fallback authorization policy, so routes mapped outside the `/api` group are not protected automatically. `EndpointInventoryTests` pins the route/method set, authorization, rate-limit and upload metadata, so any endpoint change must update it deliberately. All named ID route parameters use Guid constraints. No public document-download/list-by-arbitrary-ID endpoint exists.

## Shapes, validation and success responses

JSON uses web defaults and string enums, with integer enum values disallowed for JSON conversion. Maximum JSON depth is 32. Query/form enums (`status` on case lists, document `category`) bind case-insensitively and accept numeric strings through `EndpointConventions.ParseEnum`; services reject undefined values. A missing document `category` defaults to SupportingDocument. CSV parsing has its own rules (below). Inputs and named DTOs are records in Requests.cs; responses also include mutable entities and anonymous objects. Current public projections omit reviewer notes, audit events, organization IDs, storage keys and token hashes; retain that restricted contract.

Catalog creates return 201 with an absolute Location (named GET route); shipment create returns 201 with `{ shipment, eudrCaseId }` without CreatedAtAction. Auth returns 200 with accessToken/expiresAtUtc. Request creation/rotation returns 200 with requestId/publicUrl/expiresAtUtc (a sensitive link shown to the internal caller). Requirement review, revoke and document withdrawal return 204; close, reopen and archive return 201 with a Location to the lifecycle history, unarchive returns 200 (see "Case lifecycle"). Uploads return document/geo DTOs. Export returns application/zip with a download name; document download uses stored MIME and original basename. Geolocation GET returns the DTO, or 204 with an empty body when no geolocation exists. File responses are attachments with `Content-Disposition` filenames and no range processing.

Explicit service FluentValidation includes length limits, email shape, uppercase two-letter country format, numeric CN code length 4–10, positive quantities and enum membership. These are not registry/legal validations. OIB validation is 11 digits only. Review notes are optional; the closure DDS reference is required (max 200 after trimming) for the `ExternalDdsCompleted` outcome and rejected for the other outcomes. Parameter binding can reject malformed JSON, missing bodies or unparsable values before services. Do not move validation only to the UI.

Tenant-wide internal list endpoints that can grow without bound use the shared offset-paging convention ([ADR 0004](adr/0004-paginated-collection-endpoints.md)): `GET /api/eudr-cases`, `/api/suppliers`, `/api/products`, `/api/shipments`, `/api/producers` and `/api/production-plots`. Query `page` (default 1, >= 1) and `pageSize` (default 25, 1–100); invalid or non-integer values and a skip that overflows an integer are rejected with 400. The response is `PageResult<T>`: `{ items, page, pageSize, totalCount }`, where `totalCount` is the tenant-filtered total and a page past the end returns empty `items`. Ordering is deterministic and ends with a unique tiebreak: cases `UpdatedAtUtc` descending then ID; suppliers and products `Name` then ID; shipments `CreatedAtUtc` descending then ID. Implementation: `Common/Paging.cs` (`ToPageAsync` accepts only ordered queries). Filters: cases take `status` (a workflow status; `Completed` and `Archived` are rejected with 400), supplierId, productId, `archived` (`exclude` by default, `only` or `include`, case-insensitive; anything else is 400) and `search` <=200 characters over shipment reference/supplier/product name; suppliers take `search` <=200 over name; products take `search` <=200 over name or CN code and an optional boolean `isActive` (omitted returns active and inactive; the filter applies before `totalCount`, ordering and paging; a non-boolean value is rejected with 400); shipments have no filters; producers and production plots order by `Name` then ID and take `search` <=200 over name or external reference plus an optional boolean `isActive` (plots also an optional `producerId`; an unknown or foreign id matches nothing and returns an empty page). Per-case nested collections (documents, requirements, audit events), the dashboard and other lookup-style or bounded results stay unpaginated; a new tenant-wide list uses the helper, and anything else paginates only for a concrete growth reason.

## Retained evidence (files, geometry, details, export)

Evidence is append-only ([ADR 0005](adr/0005-retained-evidence-append-only-rows.md)); every endpoint below shows **current** evidence only.

- `DELETE /documents/{documentId}` **withdraws** the document: 204, the row and bytes are retained, audit event `DocumentWithdrawn` (historic `DocumentDeleted` events remain). Repeating it on a withdrawn document returns 204 as a no-op (no audit event, no requirement change); unknown or foreign ids stay 404; Closed and archived cases stay 409.
- `GET /documents` and `CaseDetails.documents` list current documents only. `GET /documents/{documentId}` still downloads a withdrawn document (tenant and case scoped).
- `DocumentDto.withdrawnAtUtc` and `GeoDto.supersededAtUtc` are additive (null in current-only responses). `CaseDetails.supplierSubmission` gains `supersededAtUtc` and `supplierRequestId`.
- Every geometry upload and every public `PUT .../details` creates a new row, so `GeoDto.id` and `supplierSubmission.id` change on each replacement/save (they were stable before).
- The export ZIP contains current evidence only. `manifest.json` gains `evidenceScope` (a notice that it is not a reviewed dossier snapshot) and `retainedNotIncluded` `{ withdrawnDocuments, supersededGeolocations, supersededSupplierSubmissions }`.
- `GET /api/eudr-cases/{caseId}/evidence-history` returns every retained version, newest first (`createdAtUtc` desc, then `id` desc): `{ documents: DocumentDto[], geolocations: GeoDto[], supplierSubmissions: SupplierSubmissionVersionDto[] }`. Documents carry `withdrawnAtUtc`, geolocations and submissions carry `supersededAtUtc`; the current version is the one where that field is null. `SupplierSubmissionVersionDto`: `id`, `countryOfProductionCode`, `productionPeriodFrom`, `productionPeriodTo`, `confirmedQuantity`, `notes`, `submittedAtUtc`, `supersededAtUtc`, `supplierRequestId`, `createdAtUtc` (no `organizationId`). **Unpaginated by design** as an approved pilot-scale assumption; this is not a permanent guarantee that retained history stays small, and pagination may be introduced later as a contract change.
- `GET /api/eudr-cases/{caseId}/geolocation/{geolocationId}/file` returns the original bytes of any retained geometry version of that case (`application/geo+json`, attachment named with the original file name, `nosniff`). Both routes are internal, authenticated and tenant/case scoped: unknown, other-organization or other-case ids return 404, anonymous callers 401. There are no public token history routes.

## Production provenance (producers, production plots, plot revisions)

Internal-only, authenticated routes ([ADR 0006](adr/0006-production-provenance-plot-revisions.md)); module `Endpoints/Provenance/`, service `Services/ProvenanceService.cs`, records in `Contracts/Requests.cs`, validators in `Contracts/Validators.cs`. Explicit DTOs only; no response contains `organizationId`. Handoff for clients: [frontend handoff](frontend-handoffs/2026-10-production-provenance.md).

- **Producers.** `GET /api/producers` (paginated). `POST` creates an always-active producer (201 + absolute Location). `PUT /{id}` edits `name`, `externalReference`, `countryCode`, `notes` and `isActive`, which **must be present** (omitted or null: 400, so an omission can never reactivate a producer) (descriptive edits overwrite; audit by id only). Duplicate `externalReference` in the organization: 409. No DELETE.
- **Production plots.** `GET /api/production-plots` is tenant-wide and paginated. `POST` body `{ producerId, name, externalReference?, notes?, initialRevision }` creates the plot and revision 1 in one transaction under a row lock on the producer: unknown or foreign `producerId` gives 400 `Producer was not found in your organization.`, an inactive producer 409. `PUT /{id}` edits `name`, `externalReference`, `notes`, `isActive` (**required**: omitted or null gives 400); `producerId` is immutable. No DELETE. `GET /{id}` returns the current revision with geometry; list items carry the revision summary without geometry.
- **Revisions.** `POST /{plotId}/revisions` (body `PlotRevisionInput { countryCode, geometry, areaHectares?, note? }`) locks the plot row, requires an **active plot** (409 otherwise; the producer's activity is not checked), and returns 409 when nothing material changed (geometry by topological equality, country, declared area; a note alone is not material). Otherwise the current revision is superseded and saved before the next-numbered one is inserted, in one transaction (201 + Location of the revision GET). `GET /{plotId}/revisions` lists all revisions newest first (`Number` desc) as summaries, **unpaginated** (approved pilot-scale assumption, like `evidence-history`); `GET /{plotId}/revisions/{revisionId}` returns any revision of that plot with geometry. Revisions have no PUT/DELETE.
- **Geometry.** A bare `Point`, `Polygon` or `MultiPolygon` GeoJSON object (no Feature/FeatureCollection), at most 5 MiB, serialized back as a JSON object. Structural validity only; not EUDR completeness or sufficiency (no 4 ha rule, no computed area). `countryCode` `^[A-Z]{2}$` (format only); `areaHectares` > 0 with at most 4 decimals, declared not computed.
- **Status codes.** Route-level unknown or foreign ids and a revision id of another plot: 404. Validation and geometry errors: 400. Duplicate reference, inactive producer/plot, no-op revision: 409. DELETE and revision PUT/DELETE are unmapped (405).
- **Audit.** `ProducerCreated`, `ProducerUpdated`, `ProductionPlotCreated` (also covers revision 1), `ProductionPlotUpdated`, `PlotRevisionCreated`: no case, identifiers only, never coordinates.
- There is no public/token route, and case details, export and the supplier portal are unchanged.

## Case dossier (lot, producer contributions, pinned plot revisions)

Internal-only, authenticated routes ([ADR 0007](adr/0007-case-dossier-lot-attribution.md)); module `Endpoints/Cases/CaseDossierEndpoints.cs`, service `Services/CaseDossierService.cs`, records in `Contracts/Requests.cs`, validators in `Contracts/Validators.cs`. Explicit DTOs only; no response contains `organizationId` or geometry. It records operator-entered facts only: no applicability, completeness, sufficiency or review decision, and it never changes requirement statuses or the case status. Handoff for clients: [frontend handoff](frontend-handoffs/2026-10-case-dossier-lot-sources.md).

- **`GET /api/eudr-cases/{caseId}/dossier`** returns `CaseDossierDto { id, eudrCaseId, createdAtUtc, shipmentQuantity, shipmentUnit, currentLot }` (200), **204 with no body when the case has no dossier yet**, 404 for an unknown or foreign case. `id` is the dossier id, the stable anchor of the case's one physical lot; clients should key a lot by case/dossier id. `shipmentQuantity`/`shipmentUnit` are shown alongside for comparison only; they are never enforced against the lot.
- **`PUT /api/eudr-cases/{caseId}/dossier/lot`** is a complete-replacement command: the body is the whole lot `CaseLotInput { lotReference, quantity, unit, note?, contributions: [{ producerId, quantity, unit, plots: [{ productionPlotId, plotRevisionId, productionStartDate?, productionEndDate? }] }] }`. The first save creates the dossier and lot number 1; a later material change supersedes the current lot and inserts number + 1 (200 `CaseDossierDto`). There are no nested contribution/plot routes, no POST and no DELETE (405).
- **Order of checks.** The route case is resolved and locked first (404, whatever the body contains), then a Closed or archived case is rejected (409), and only then is the body validated (400). Syntactically malformed JSON may still be rejected by the framework with 400 before the handler runs.
- **Normalization and validation.** `lotReference` is trimmed (required, max 100); a blank `note` becomes null (max 4000). `quantity` > 0, < 1e14, at most 6 decimals, for the lot and every contribution. `unit` must be defined and not `Other`; a contribution `unit` must equal the lot `unit` (no conversion: Kg and Ton never mix). No duplicate `producerId` in a lot and no duplicate `productionPlotId` in a contribution. Caps: 200 contributions, 500 plot links per contribution, 5000 links in total. Production period: both dates omitted, or both given with start <= end (equal dates express a single day); one date alone is 400. These are structural checks only, with no cut-off-date, 4 ha or sufficiency rule.
- **Quantity reconciliation** is derived on read and never stored: `QuantityReconciliationDto { allocatedQuantity, remainingQuantity, status }` with `status` `Reconciled` (sum of contributions == lot quantity, exact decimal equality, so `1.5` equals `1.500000`) or `UnderAllocated` (including no contributions; storable). A sum above the lot quantity is 400 and nothing is saved. There is no tolerance. This lot-level DTO compares the contributions only; the lot is compared with the shipment and the supplier-confirmed quantity by the completeness `quantityReconciliation` (see "Completeness", [ADR 0010](adr/0010-quantity-reconciliation-v1.md)).
- **Provenance references.** Body ids are resolved inside the caller's organization: an unknown or foreign producer, plot or revision is a non-disclosing 400 (`... was not found in your organization.`); a plot that does not belong to the contribution's producer, or a revision that is not of the submitted plot, is 400. The submitted `plotRevisionId` is the historical pin: it is never replaced by the plot's current revision and a superseded revision is a valid target. The database enforces the same producer -> plot -> revision chain.
- **Active / carry-over rule.** A contribution or plot link that is new relative to the current lot version needs an active producer and an active plot, otherwise 409. A source carried over from the current version (same producer; same producer + plot + exact revision) stays usable after deactivation, and its contribution quantity and production period may be corrected. Adding a producer, adding a plot, or pinning a different revision (even of an inactive plot) is new. Producers and plots are locked `FOR SHARE` (by id, after the case lock) so a concurrent deactivation is serialized with the decision.
- **`lotReference` uniqueness.** It is a versioned business/batch reference, not a permanent lot identity. It is unique among **current** lots in the organization: another case's current reference is 409 (`Lot reference is already used by another case in your organization.`; a race is also 409). The same case may keep it across versions, and a reference that is no longer current may be reused, including by another case; another organization is unaffected.
- **Idempotency.** An identical PUT returns 200 with the same current lot id, creates no version and writes no audit event. Equality is order-independent after normalization (contributions are a set keyed by `producerId`, plot links a set keyed by `(productionPlotId, plotRevisionId)` with their period); any changed value, producer, plot, revision or period is a new version.
- **`GET .../dossier/lot-history`** returns `CaseLotDto[]` newest first (`number` descending; `[]` when there is no dossier; 404 for an unknown or foreign case), **unpaginated** (approved per-case pilot-scale assumption, like `evidence-history`). Exactly one entry has `supersededAtUtc: null`.
- **DTOs.** `CaseLotDto { id, number, lotReference, quantity, unit, note, reconciliation, contributions, createdByUserId, createdAtUtc, supersededAtUtc }`; `LotContributionDto { id, producerId, producerName, producerIsActive, quantity, unit, plots }` (ordered by producer name then id); `ContributionPlotDto { id, productionPlotId, plotName, plotIsActive, plotRevisionId, revisionNumber, countryCode, geometryType, areaHectares, revisionSupersededAtUtc, productionStartDate, productionEndDate }` (ordered by plot name then id). Enums are strings, dates `yyyy-MM-dd`, decimals JSON numbers. Names, `isActive` flags and revision metadata are live master data, not snapshots.
- **Shipment lock.** `PUT /api/shipments/{id}` returns 409 once the case has a dossier (in addition to the supplier-request and evidence conditions); shipment creation is unchanged. There is no shipment DELETE (405): archive is a case-level lifecycle action.
- **Audit.** `CaseLotSaved` (case-scoped, ids only: `Case lot version {id} (number N) saved; superseded {previousId}.`), never geometry, coordinates or the request payload. The case `updatedAtUtc` is bumped on a real new version.
- **Export.** See "Export contract": `manifest.json` gains `dossier`, `dossierScope` and `retainedNotIncluded.supersededLotVersions`, and the package gains `plots/{plotRevisionId:N}.geojson` for the current lot's pinned revisions.
- **Status codes.** 401 anonymous; 404 unknown/foreign route case; 400 validation, body-id, unit, period and over-allocation errors; 409 closed or archived case, inactive new producer/plot, duplicate current `lotReference`, shipment edit after a dossier exists; 405 DELETE. There is no public/token route and `GeoSubmission` is untouched.

## Completeness facts (operator profile, case master data, applicability, recipients, evidence links)

Internal-only, authenticated routes ([ADR 0008](adr/0008-completeness-facts-and-reviewed-history.md)); modules `Endpoints/Compliance/OperatorProfileEndpoints.cs` and `CaseFactEndpoints.cs`, services `OperatorProfileService`, `CaseMasterDataService`, `CaseApplicabilityService`, `CaseRecipientService`, `CaseEvidenceLinkService`, records in `Contracts/Requests.cs`, validators in `Contracts/Validators.cs`. Explicit DTOs only; no response contains `organizationId`. They record entered or assessed facts only: no completeness, sufficiency, compliance or review decision, and they never change requirement statuses or the case status. Any authenticated member may call them (the only owner-only route is `POST ./reviews`, see "Reviews"). `GET completeness` and the review routes are documented in "Completeness" and "Reviews" below. There is no public/token route.

- **Common write protocol (`PUT` applicability/recipients, `POST` refresh and evidence links, `DELETE` link).** The route case is resolved and locked first (404, whatever the body contains), then a Closed or archived case is rejected (409), and only then is the body validated (400). Syntactically malformed JSON or an unknown enum name may still be rejected by the framework with 400 before the handler runs. Identical normalized content is a 200 no-op (no new version, no audit event, no `updatedAtUtc` change). Dates are ISO `yyyy-MM-dd`; enums are strings. Audit events carry identifiers only.
- **`GET /api/operator-profile`** returns `OperatorProfileDto { id, legalName, postalAddress, email, establishmentCountryCode, eoriNumber, updatedByUserId, createdAtUtc, updatedAtUtc }` (200) or **204** when the organization has none. **`PUT`** is an upsert of the complete profile (200 `OperatorProfileDto`); `legalName` (max 200), `postalAddress` (max 1000), `email` (valid, max 256) and `establishmentCountryCode` (two uppercase letters) are required, `eoriNumber` is optional (uppercase letters/digits, max 17) and only stored. Audit `OperatorProfileSaved` (profile id only). There is no DELETE (405). Saving it changes no case: cases pick it up only through a master-data refresh.
- **`GET .../master-data`** returns `CaseMasterDataDto { current, shipmentMatch, drift[] }` (200), **204** when the case has no copy, 404 for an unknown or foreign case. `current` is `CaseMasterDataVersionDto { id, number, operator { legalName, postalAddress, email, establishmentCountryCode, eori }, supplier { supplierId, name, postalAddress, email, countryCode }, product { productId, cnCode, commodity, name, catalogueDescription }, createdByUserId, createdAtUtc, supersededAtUtc }`; operator values are null when no profile existed at copy time. `shipmentMatch` is `false` when the copy's supplier or product differs from the case's **current** shipment (a shipment may change them until it is locked). `drift` is `[{ area: Operator|Supplier|Product, fields: [camelCase names] }]` over fact-bearing fields (operator: legalName, postalAddress, email, establishmentCountryCode, eori; supplier: name, postalAddress, email, countryCode; product: cnCode, commodity), empty when none; product `name` and `catalogueDescription` never drift. Drift is advisory and read-only.
- **`POST .../master-data/refresh`** (no body) copies the operator profile and the shipment's current supplier and product into a new version and returns the same `CaseMasterDataDto` (200). If every copied field, context fields included, equals the current copy the existing version is returned unchanged. Otherwise the previous version is superseded and `number + 1` inserted (audit `CaseMasterDataRefreshed`, case `updatedAtUtc` bumped). 404 unknown/foreign case; 409 Closed or archived.
- **`GET .../master-data-history`** returns `CaseMasterDataVersionDto[]` newest first (`[]` when none; 404 unknown/foreign), unpaginated (per-case pilot scale).
- **`GET .../applicability`** returns `CaseApplicabilityDto { status, current }` (200), 204 when nothing is recorded, 404 unknown/foreign. `status` is derived on read (never stored): `NotRecorded | ProductChanged | Pending | OutsideRegulatoryScope | UnsupportedFlow | WithinSupportedScope`, see [EUDR_DOMAIN](EUDR_DOMAIN.md). `current` is `CaseApplicabilityVersionDto { id, number, assessedProductId, assessedCnCode, assessedCommodity, productDescription, singleRelevantCommodity, activityType, operatorRole, operatorRoleDescription, activityDate, activityDateKind, scopeCitation, qualifications, legalBasisVersion, effectiveDate, reasoning, regulatoryScope, flowSupport, decidedByUserId, decidedAtUtc, createdByUserId, createdAtUtc, supersededAtUtc }`.
- **`PUT .../applicability`** is a complete-replacement command: `{ productDescription?, singleRelevantCommodity, activityType: PlacingOnMarketByImport|PlacingOnMarketDomestic|Export, operatorRole: Operator|OtherUnsupported, operatorRoleDescription?, activityDate?, activityDateKind: Planned|Actual, scopeCitation?, qualifications?, legalBasisVersion?, effectiveDate?, reasoning?, regulatoryScope: Pending|InScope|OutsideRegulatoryScope, flowSupport: Pending|Supported|UnsupportedFlow }` (200 `CaseApplicabilityDto`). The assessed product identity and the decision stamp are **server-set** (from the case's current master-data copy; any such client field is ignored). Order: route case (404), closed or archived (409), body validation (400), then the copy: no copy, or a copy that does not match the current shipment, is **409 `Refresh the case master data first.`** Validation: text is trimmed and blank optionals become null; `productDescription` max 2000 and required when `regulatoryScope` is `InScope`; `operatorRoleDescription` max 500, required and nonblank for `OtherUnsupported`, rejected (400) for `Operator`; `scopeCitation` max 1000, `legalBasisVersion` max 200, `reasoning` max 4000, `qualifications` max 2000; when `regulatoryScope` is not `Pending`, `scopeCitation`, `legalBasisVersion`, `reasoning`, `effectiveDate` and `activityDate` are required. `flowSupport` may stay `Pending` for `OutsideRegulatoryScope` and is ignored there. A material change supersedes the current version (`number + 1`, audit `CaseApplicabilitySaved`); resubmitting after a supplier-only or operator-only refresh is a no-op, while a different product (assessed id, CN code or commodity) is a new version. No DELETE.
- **`GET .../applicability-history`** returns `CaseApplicabilityVersionDto[]` newest first (`[]`; 404), unpaginated.
- **`GET .../recipients`** returns `CaseRecipientStatementDto { id, number, resolution, notApplicableBasis, recipients: [{ id, name, postalAddress, email }], createdByUserId, createdAtUtc, supersededAtUtc }` (200), 204 when **unresolved** (no statement), 404 unknown/foreign. Recipients are ordered by name, postal address, e-mail (ordinal) then id. **`PUT`** is a complete replacement `{ resolution: RecipientsIdentified|NotApplicable, notApplicableBasis?, recipients?: [{ name, postalAddress, email }] }`: `RecipientsIdentified` needs 1-50 recipients with a name (max 200), postal address (max 1000) and valid e-mail (max 256) and no basis; `NotApplicable` needs a nonblank basis (max 2000) and no recipients; anything else is 400, and a missing list is never turned into `NotApplicable`. Identical content in any recipient order is a no-op; otherwise a new version (audit `CaseRecipientsSaved`, no recipient data). **`GET .../recipients-history`** returns the statements newest first (`[]`; 404), unpaginated. No DELETE.
- **`GET .../evidence-links`** returns `CaseEvidenceLinkDto[] { id, caseDocumentId, purpose, note, documentFileName, documentWithdrawnAtUtc, createdByUserId, createdAtUtc, withdrawnAtUtc, withdrawnByUserId }` for **all** links of the case, withdrawn ones included, oldest first (404 unknown/foreign). `withdrawnAtUtc`/`withdrawnByUserId` are null for a current link; the link's withdrawal and the linked document's withdrawal (`documentWithdrawnAtUtc`) are separate facts. Only links with `withdrawnAtUtc: null` to non-withdrawn documents count as current. **`POST`** `{ caseDocumentId, purpose: Legality|DeforestationFree|Applicability|ProductionSource, note? (max 1000) }` returns **201** with the link in the body and **no `Location` header** (there is no GET-by-id route). A document that is unknown, foreign or belongs to another case is the same non-disclosing **400**; a withdrawn document is 409; a second current link for the same document and purpose is 409; a Closed or archived case is 409. One document may serve several purposes. **`DELETE .../evidence-links/{linkId}`** withdraws the link (the row is retained) and returns 204; withdrawing an already withdrawn link is an idempotent 204; an unknown, foreign or other-case link is 404; closed or archived case 409. A link means only "offered for this purpose": it is not review, sufficiency, compliance or deforestation-free status, and linking or withdrawing changes no requirement or case status. Audit `CaseEvidenceLinked` / `CaseEvidenceLinkWithdrawn` (ids only).
- **Supplier postal address.** `SupplierInput` gains an optional trailing `postalAddress` (max 1000, trimmed, blank becomes null) and the supplier response gains `postalAddress`. The supplier CSV header is unchanged and imports leave it null. As with the other optional supplier fields, a PUT that omits it clears it.
- **Status codes.** 401 anonymous; 404 unknown/foreign route case or link; 400 validation and unknown/foreign/other-case document ids; 409 closed or archived case, `Refresh the case master data first.`, withdrawn document, duplicate current link; 405 for unmapped methods (DELETE on the profile and on the versioned resources). A supplier or product referenced by any master-data copy or applicability can no longer be deleted (the generic referenced-record 409).

## Completeness (current working dossier, policy v2)

`GET /api/eudr-cases/{caseId}/completeness` (module `Endpoints/Compliance/CaseFactEndpoints.cs`, service `Services/CompletenessService.cs`; [ADR 0008](adr/0008-completeness-facts-and-reviewed-history.md)). Internal, authenticated, **read-only**: it writes nothing (no audit event, no `updatedAtUtc` change), takes no lock (it reads one repeatable-read snapshot) and never changes requirements or the case status. 401 anonymous, 404 unknown or foreign case, 405 for other methods. Computed on every call, never stored. It states whether the *recorded facts* satisfy a versioned pilot policy; it is **not** a legal-compliance, risk, deforestation-free, safety or DDS-readiness determination.

```json
{
  "policy": { "id": "provena-pilot-completeness", "version": "2", "limitations": ["..."] },
  "evaluatedAtUtc": "2026-10-14T09:00:00+00:00",
  "fingerprint": "2cc06ed4…(64 lower-case hex)", "fingerprintVersion": 1,
  "applicability": { "status": "WithinSupportedScope", "currentVersionId": "…" },
  "dataCoverage": "Incomplete",
  "evidenceReadiness": "AwaitingRequirementDecisions",
  "reviewFreshness": "None",
  "latestReview": null,
  "advisories": [ { "code": "CATALOGUE_DRIFT_SUPPLIER", "area": "Supplier", "subjectId": null, "message": "…" } ],
  "items": [ { "code": "LOT_RECONCILED", "group": "Quantity", "subjectType": "CaseLot", "subjectId": "…", "status": "Invalid", "reason": "Producer contributions (6 Kg) do not equal the lot quantity (10 Kg); remaining 4 Kg." } ],
  "quantityReconciliation": { "outcome": "QuantityMismatch", "checks": [ "..." ] }
}
```

- **Three separate axes, no combined verdict.** `dataCoverage` (`Complete | Incomplete`) is `Incomplete` when any item of the groups `MasterData`, `Applicability`, `Product`, `Quantity`, `Production`, `Parties` is `Missing` or `Invalid`; `Evidence` items never decide it. `evidenceReadiness` (`EvidenceMissing | AwaitingRequirementDecisions | ReadyForOwnerReview`) is `EvidenceMissing` when any `Evidence` item is `Missing` or `Invalid`, else `AwaitingRequirementDecisions` when any is `AwaitingReview`, else `ReadyForOwnerReview`. There is no "Reviewed" value anywhere. `reviewFreshness` (`None | Current | Stale`) and `latestReview` describe the latest human review (see "Reviews"): `None`/`null` before the first review. A reviewed state exists only as `latestReview.decision` together with `reviewFreshness`; there is no "Reviewed" evidence-readiness value.
- **Items.** `status` is `Satisfied | Missing | Invalid | AwaitingReview | NotApplicable`; `subjectType`/`subjectId` identify the row an item is about (null for case-level items); `reason` says exactly what was checked. Codes (stable, one item each unless noted): `MASTER_DATA_SHIPMENT_MATCH`; `APPLICABILITY_RECORDED`, `APPLICABILITY_DECIDED`, `APPLICABILITY_PRODUCT_MATCH`, `APPLICABILITY_IN_SCOPE`, `FLOW_SUPPORTED`; `PRODUCT_DESCRIPTION`, `PRODUCT_CN_CODE`; `LOT_PRESENT`, `SHIPMENT_LOT_QUANTITY_MATCH`, `SUPPLIER_CONFIRMED_QUANTITY_MATCH`, `LOT_RECONCILED` (in this order); `SOURCE_HAS_PLOT` (one per contribution), `SOURCE_PRODUCTION_PERIOD` (one per plot link), `SOURCE_GEOLOCATION_FORM` (one per distinct pinned revision); `PARTY_OPERATOR`, `PARTY_SUPPLIER_NAME`, `PARTY_SUPPLIER_POSTAL_ADDRESS`, `PARTY_SUPPLIER_EMAIL`, `PARTY_RECIPIENTS`; `REQUIREMENT_<RequirementType>` (six, e.g. `REQUIREMENT_Geolocation`), `EVIDENCE_LEGALITY_PRESENT`, `EVIDENCE_DEFORESTATION_FREE_PRESENT`. Items are always emitted (a missing prerequisite makes them `Missing`), in a deterministic order.
- **`quantityReconciliation`** (additive member of the response and of the working-export manifest `completeness`; [ADR 0010](adr/0010-quantity-reconciliation-v1.md)). Derived on every call, never stored, never overridden. `{ outcome, checks[] }` with `outcome` `Matched | MissingData | UnitMismatch | QuantityMismatch` (precedence `UnitMismatch` > `QuantityMismatch` > `MissingData`) and exactly three checks in this order: `SHIPMENT_LOT` (shipment vs the current lot), `SUPPLIER_CONFIRMED_SHIPMENT` (supplier-confirmed quantity vs shipment) and `CONTRIBUTIONS_LOT` (sum of producer contributions vs lot). A check is `{ code, status, expected, actual, difference, missingFields, reason }` with `status` `Matched | MissingData | UnitMismatch | QuantityMismatch | NotApplicable`, `expected`/`actual` `{ source, quantity, unit, unitImplied }` (`quantity`/`unit` may be null when missing; `source` is `Shipment | CaseLot | SupplierSubmission | ProducerContributions`), `difference` = `actual - expected` (null unless both sides are present in the same unit) and `missingFields` camelCase names (`caseLot`, `producerContributions`, `supplierConfirmedQuantity`, `quantityConfirmationWaiverBasis`). **Pilot single-lot assumption:** Shipment == current CaseLot holds because one shipment/case has one current lot; it is not a permanent multi-lot rule. Exact decimal equality in one unit (`10` equals `10.000000`), no unit conversion, no tolerance; the supplier-confirmed quantity has no unit and is taken to be in the shipment unit (`unitImplied: true`). Every existing confirmed quantity is compared. With none: requirement `NotRequired` with a nonblank reviewer note -> `NotApplicable`; `NotRequired` without one -> `MissingData` (`quantityConfirmationWaiverBasis`); anything else -> `MissingData` (`supplierConfirmedQuantity`). `IsRequired` is not consulted. Item mapping: `MissingData` -> `Missing`, `UnitMismatch`/`QuantityMismatch` -> `Invalid`, `NotApplicable` -> `NotApplicable`, `Matched` -> `Satisfied`. A non-matched outcome makes `dataCoverage` `Incomplete` and blocks `AcceptedAsCompleteUnderPolicy` (see "Reviews"); it does not block `ConfirmedOutsideRegulatoryScope`, `ConfirmedUnsupportedFlow` or `ReturnedForCorrection`. Closing as `ExternalDdsCompleted` also needs `Matched` (see "Case lifecycle"). The fingerprint (version 1) and review snapshot (schema 1) are unchanged.
- **Rules (policy v2).** `MASTER_DATA_SHIPMENT_MATCH`: `Missing` without a case master-data copy, `Invalid` when the copy's supplier or product differs from the shipment's current ones (refresh needed), else `Satisfied`. Applicability items use the derived status ([EUDR_DOMAIN](EUDR_DOMAIN.md)); `APPLICABILITY_IN_SCOPE` is `Invalid` for a recorded outside-scope decision ("outside this policy's scope", not a non-compliance finding) and `FLOW_SUPPORTED` is then `NotApplicable`. `PRODUCT_DESCRIPTION` reads only `CaseApplicability.ProductDescription` (never the catalogue `Product.Description`); `PRODUCT_CN_CODE` checks format only (4-10 digits). The four Quantity items come from the derived quantity reconciliation (previous bullet): exact decimal equality, no conversion, no tolerance. Production: both period dates per link (presence only); geolocation form by the declared area only (Polygon/MultiPolygon `Satisfied`; Point `Satisfied` at a declared area of at most 4 ha, `Missing` without one, `Invalid` above 4 ha; no area calculation, no coordinate precision). Parties are read from the case master-data copy (EORI is not evaluated); `PARTY_RECIPIENTS`: no statement is `Missing` (unresolved), identified recipients `Satisfied`, `NotApplicable` with a recorded basis `NotApplicable`. Requirements: `Accepted` -> `Satisfied` (a requirement-level decision, not a dossier review), `Submitted` -> `AwaitingReview`, `Missing` -> `Missing`, `Rejected` -> `Invalid`, `NotRequired` with a note -> `NotApplicable`, `NotRequired` without a note -> `Missing`. `EVIDENCE_*_PRESENT` is `Satisfied` only with at least one non-withdrawn link of that purpose whose document is itself current; it is presence only, never a sufficiency finding.
- **`fingerprint` / `fingerprintVersion`.** SHA-256 (lower-case hex) of the canonical serialization of the case's *facts* (version 1; see [EUDR_DOMAIN](EUDR_DOMAIN.md) for inputs and exclusions). It changes exactly when a fact changes: not for catalogue edits (advisories), a context-only master-data refresh, producer/plot labels, a superseded pinned revision, the case status or audit/export activity. Section hashes are computed internally and not exposed yet.
- **`advisories`** never affect the axes or the fingerprint: `CATALOGUE_DRIFT_OPERATOR|SUPPLIER|PRODUCT` (`area` set; the live catalogue differs from the case copy in fact-bearing fields) and `PINNED_REVISION_SUPERSEDED` (`area` `Lot`, `subjectId` the superseded revision id the current lot still pins). On a Closed or archived case the message says it is shown after case closure and the reviewed record is unaffected.
- A case may be `ReadyForExport` or `Closed` while `dataCoverage` is `Incomplete`: completeness is independent of the operational status, and closing is gated by a Current Owner review, not by completeness directly.

## Reviews (immutable reviewed dossier history, reviewed export)

Internal, authenticated routes ([ADR 0008](adr/0008-completeness-facts-and-reviewed-history.md)); module `Endpoints/Compliance/ReviewEndpoints.cs`, services `ReviewService` (create), `ReviewReadService` (reads), `ReviewFreshnessService`, `ReviewedExportService`. A review is a human decision on exactly the dossier the Owner loaded; it never changes requirements or the case status by itself (the latest Current review is what an Owner closes the case on, see "Case lifecycle"), and no decision is a legal-compliance determination, risk assessment, release or DDS statement. No response contains `organizationId`.

- **`POST /api/eudr-cases/{caseId}/reviews`** (Owner only) with `{ decision, rationale, expectedFingerprint, expectedLatestReviewId? }` returns **201** with `ReviewDetailDto` and a `Location` header for `GET .../reviews/{reviewId}`. `decision`: `AcceptedAsCompleteUnderPolicy | ConfirmedOutsideRegulatoryScope | ConfirmedUnsupportedFlow | ReturnedForCorrection` (strings only). `rationale` is required (trimmed, max 4000). `expectedFingerprint` is the `fingerprint` returned by `GET completeness` (64 hex characters). `expectedLatestReviewId` is the `latestReview.reviewId` the client loaded, or `null`/omitted when the client loaded the case with no review.
- **Order of checks (a contract).** (1) live Owner membership check - **403 for a Member whatever the case id or body**: an existing, nonexistent or foreign case and an invalid or malformed body all answer 403, so nothing about the case is disclosed and the body is not even parsed; the JWT role is not trusted (a demoted Owner is denied at once); (2) unknown or foreign case 404; (3) a Closed case is 409 `Closed cases cannot be changed; reopen the case first.` and an archived case 409 `Archived cases cannot be changed; unarchive the case first.`; (4) body validation 400 (undefined/integer enum, blank or over-long rationale, malformed fingerprint, malformed JSON; a non-JSON content type is 415); (5) `expectedFingerprint` or `expectedLatestReviewId` differs from the current state 409 `Dossier or review history changed since it was loaded`; (6) unmet decision precondition 409.
- **Optimistic concurrency.** The case is locked and the live catalogue sources locked `FOR SHARE` while the current fingerprint and the actual latest review (highest revision number) are resolved, so the Owner reviews exactly what they loaded: `expectedLatestReviewId` null matches only when no review exists; an id matches only the actual latest review. Two simultaneous requests for the same state give one 201 and one 409. A catalogue edit that commits first shows up as drift (acceptance then fails with 409); one that arrives later waits.
- **Decision preconditions** (409; the problem `errors` object is `{ reason, failingItems: [{ code, subjectType, subjectId, status, reason }] }`): `AcceptedAsCompleteUnderPolicy` needs `MASTER_DATA_SHIPMENT_MATCH` satisfied, applicability `WithinSupportedScope`, no item `Missing`, `Invalid` or `AwaitingReview` (`NotApplicable` is fine) and no catalogue drift (unadopted drift is stated in `reason`, never as a failing item); `ConfirmedOutsideRegulatoryScope` needs a satisfied shipment match and applicability `OutsideRegulatoryScope` (flow support may stay Pending; the InScope completeness set is not required); `ConfirmedUnsupportedFlow` needs a satisfied shipment match and applicability `UnsupportedFlow` (including `OperatorRole = OtherUnsupported`); `ReturnedForCorrection` is always allowed, even with a shipment mismatch or an incomplete dossier. **Every `failingItems[].code` is a real completeness item code** (the same codes and statuses as `GET completeness`); requirements that have no failing item - a derived applicability status that is not the one the decision needs, or catalogue drift - are stated in `reason` (for example "The derived applicability status is WithinSupportedScope; ConfirmedOutsideRegulatoryScope requires OutsideRegulatoryScope."); no pseudo-item codes exist. `ProductChanged` blocks the three positive decisions (`APPLICABILITY_PRODUCT_MATCH` is then a failing item).
- **`GET .../reviews`** (any member) returns `ReviewSummaryDto[] { reviewId, caseRevisionId, revisionNumber, decision, reviewerUserId, reviewedAtUtc, policyId, policyVersion, fingerprint, fingerprintVersion }` newest first by `revisionNumber`, unpaginated (per-case pilot scale). 404 unknown or foreign case.
- **`GET .../reviews/{reviewId}`** (any member) returns `ReviewDetailDto { reviewId, caseRevisionId, revisionNumber, decision, rationale, reviewerUserId, reviewedAtUtc, policyId, policyVersion, snapshotSchemaVersion, fingerprintVersion, fingerprint, sectionHashes, pins, snapshot }`. `pins` lists the pinned row ids (`caseDossierId`/`caseLotId` are both null or both set; `documentIds`, `evidenceLinkIds`). `snapshot` is the stored `CaseRevisionSnapshotV1 { schemaVersion, facts, context, completeness }`: `facts` are the fingerprinted content (shipment, fact-bearing master data, applicability, recipients, lot with exact pinned revisions, evidence, requirements incl. review provenance), `context` is frozen labels and catalogue context (producer/plot names, `productName`, `productCatalogueDescription`, `pinnedRevisions[].supersededAtReviewTime`, `catalogueDrift`) and `completeness` is the evaluation relied on. It is read from storage and never changes. 404 for an unknown or foreign case, an unknown review or a review of another case.
- **`GET .../reviews/{reviewId}/export`** (any member) returns `application/zip`: root `case-{reference}-review-{revisionNumber}/` with `review.json` (decision, rationale, reviewer, policy, fingerprint, versions, section hashes, the stored snapshot, `exportedAtUtc` and a notice "Reviewed dossier snapshot under policy ...; not a legal compliance determination, risk assessment or DDS."), `plots/{revisionId:N}.geojson` for each exact pinned plot revision, `documents/{id:N}-{name}` for each pinned document (also if withdrawn after the review) and `geolocation/original.geojson` from the pinned geolocation. Everything comes from the stored revision; party and product values are the master-data copy frozen at review time, never the live catalogue; no case lock is taken. Audit `CaseReviewExported` (ids only). Contrast: the working export (`GET .../export`) is the current working dossier and carries the live `completeness` and `latestReview`.
- **Completeness.** `reviewFreshness` is `None` (no review), `Current` or `Stale`; `latestReview` is `null` or `{ reviewId, caseRevisionId, decision, reviewedAtUtc, policyVersion, policyChanged, changedAreas }`. Freshness is computed by rebuilding the current facts and fingerprinting them with the review's stored `fingerprintVersion`; `changedAreas` lists the differing sections (`Shipment`, `MasterData`, `Applicability`, `Recipients`, `Lot`, `Requirements`, `Evidence`) when `Stale`. `policyChanged` is informational and never makes a review stale. A reviewed state exists only as `latestReview.decision` together with `reviewFreshness`; there is no "Reviewed" evidence-readiness value.
- **Status codes.** 401 anonymous; 403 Member on POST (before case and body); 404 unknown/foreign case, review or a review of another case; 400 body validation; 415 non-JSON POST body; 409 closed or archived case, fingerprint or latest-review mismatch, unmet precondition; 405 for PUT/PATCH/DELETE.

## Case lifecycle (close, reopen, archive, unarchive, history)

Internal, authenticated routes ([ADR 0009](adr/0009-case-lifecycle-v2.md)); module `Endpoints/Cases/CaseLifecycleEndpoints.cs`, services `CaseLifecycleService` (writes) and `CaseLifecycleReadService` (history), pure rules `CaseClosurePolicy`, shared gate `OwnerGate`, records in `Contracts/Lifecycle.cs`, validators in `Contracts/Validators.cs`. Explicit DTOs only; no response contains `organizationId`. Closing is not a legal-compliance, risk, release or DDS-submission decision. Handoff for clients: [frontend handoff](frontend-handoffs/2026-10-case-lifecycle-v2.md).

| Route | Who | Body | Success |
| --- | --- | --- | --- |
| `POST /api/eudr-cases/{caseId}/close` | Owner | `{ expectedReviewId, externalDdsReference? }` | **201** `CaseClosureDto`, Location = `GET .../lifecycle` |
| `POST /api/eudr-cases/{caseId}/reopen` | Owner | `{ expectedClosureId, reason }` | **201** `CaseReopeningDto`, Location as above |
| `POST /api/eudr-cases/{caseId}/archive` | Owner | `{ reason }` | **201** `CaseArchivalDto`, Location as above |
| `POST /api/eudr-cases/{caseId}/unarchive` | Owner | `{ reason }` | **200** `CaseArchivalDto` |
| `GET /api/eudr-cases/{caseId}/lifecycle` | any member | - | **200** `CaseLifecycleDto` |

- **Order of checks for every write (a contract).** (1) live `OrganizationUsers` Owner check (`OwnerGate`; the JWT role is not trusted and a demoted Owner is denied at once): **403 for a Member whatever the case id or body** - an existing, nonexistent or foreign case and an invalid, malformed or missing body all answer 403, and the body is not read; (2) unknown or foreign case 404; (3) state preconditions 409; (4) body shape 400 (a non-JSON content type is 415, a malformed JSON body is 400); (5) the optimistic and business checks below. The body is read by the handler after step 1, so a Member never learns whether the case or the body was valid, and the 415/400 body errors appear only once the state preconditions pass (for example `reopen` on a case that is not closed answers 409 first). All four writes run in one transaction under the case lock `FOR UPDATE`, which serializes them with every other case write; two identical simultaneous requests give one success and one 409.
- **`close`.** Preconditions in order: archived -> 409 `Archived cases cannot be changed; unarchive the case first.`; already closed -> 409 `The case is already closed.`. Body: `expectedReviewId` required and non-empty, `externalDdsReference` at most 200 characters after trimming (blank means absent) -> 400 (`errors.ExpectedReviewId`, `errors.ExternalDdsReference`). Then the review checks: no review -> 409 `No Owner review exists for this case; record a review before closing it.`; `expectedReviewId` is not the latest review (highest revision number, never a timestamp) -> 409 `Review history changed since it was loaded`; the review already backs a closure (also after a reopen) -> 409 `This review already backs a closure; record a new review before closing the case again.`; the review decision is `ReturnedForCorrection` -> 409 `A review that returned the dossier for correction cannot close the case.`; the legacy-reference rule for the derived outcome -> 400 `errors.ExternalDdsReference` (a supplied reference is rejected for `OutsideRegulatoryScope` and `UnsupportedFlow`; it is optional for `ExternalDdsCompleted`, see "External DDS records"); then freshness: the review must be `Current` for the present dossier (computed under the case lock with the review's stored fingerprint version; catalogue drift and `policyChanged` do not matter), otherwise 409 `The latest review is stale; record a new review of the current dossier before closing the case.` with `errors: { reason: "StaleReview", changedAreas: [...] }` (the same section names as `latestReview.changedAreas`). `ReadyForExport` is not required. Then the quantity gate: when the derived outcome is `ExternalDdsCompleted` and the CURRENT quantity reconciliation (same facts, same lock, also for a Current review made under policy v1) is not `Matched` -> 409 with `errors: { reason: "QuantityNotReconciled", quantityReconciliation }` and nothing is written; `OutsideRegulatoryScope` and `UnsupportedFlow` have no quantity gate. Last, the External DDS gate ([ADR 0011](adr/0011-external-dds-record-v1.md)) for `ExternalDdsCompleted`: no current External DDS record -> 409 `errors: { reason: "ExternalDdsRecordMissing", externalDds: null }`; the current record belongs to a review other than the latest one -> 409 `ExternalDdsReviewMismatch`; a supplied `externalDdsReference` that differs from the record's `referenceNumber` after trimming (exact, case-sensitive) -> 409 `ExternalDdsReferenceMismatch` (the last two carry `errors.externalDds { recordId, reviewId, referenceNumber, submittedAtUtc }`, never the verification number); nothing is written. The closure stores the record's `referenceNumber` as `externalDdsReference`. On success the next closure `Number` is inserted, the workflow status becomes `Closed`, active supplier requests are revoked, audit `CaseClosed` is written (identifiers incl. the External DDS record id for `ExternalDdsCompleted`, outcome and previous status; never the DDS reference or the verification number) and `updatedAtUtc` is bumped.
- **Outcome mapping.** `AcceptedAsCompleteUnderPolicy` -> `ExternalDdsCompleted`; `ConfirmedOutsideRegulatoryScope` -> `OutsideRegulatoryScope`; `ConfirmedUnsupportedFlow` -> `UnsupportedFlow`; `ReturnedForCorrection` cannot close. The client never sends an outcome.
- **`reopen`.** Preconditions: archived -> 409 (same message as above); not `Closed` -> 409 `The case is not closed.`. Body: `expectedClosureId` required and non-empty, `reason` required, non-blank, at most 4000 characters after trimming -> 400. Then: no open closure -> 409 `The case has no open closure to reopen.`; `expectedClosureId` is not the current (highest-`Number`) closure -> 409 `Closure history changed since it was loaded`. On success a `CaseReopening` is inserted and the status is re-derived from requests and requirements (`Draft`, `WaitingForSupplier`, `ReviewNeeded` or `ReadyForExport`); audit `CaseReopened` carries identifiers and the new status, not the reason. Closures, reviews, exports, DDS references and audit history are untouched, and revoked supplier links are **not** restored (a member creates a new supplier request when needed). Closing again needs a new review.
- **`archive`.** Precondition: already archived -> 409 `The case is already archived.`. Body: `reason` required, non-blank, at most 4000 characters -> 400. Works in any workflow state (a Closed case stays Closed) and never changes the workflow status. Inserts the next `CaseArchival` period, revokes active supplier requests, audit `CaseArchived` (identifiers, status and revoked count; not the reason).
- **`unarchive`.** Precondition: not archived -> 409 `The case is not archived.`. Body: `reason` as for archive -> 400. Sets the one-way retirement marker with the actor and reason on the current period; audit `CaseUnarchived`. The workflow status is whatever it was and supplier links stay revoked.
- **DTOs** (camelCase, string enums, ISO 8601 timestamps):
  - `CaseClosureDto { closureId, number, outcome: ExternalDdsCompleted|OutsideRegulatoryScope|UnsupportedFlow, reviewId, reviewRevisionNumber, reviewDecision, externalDdsReference (string|null), closedByUserId, closedAtUtc, reopening (CaseReopeningDto|null) }`.
  - `CaseReopeningDto { reopeningId, closureId, reason, reopenedByUserId, reopenedAtUtc }`.
  - `CaseArchivalDto { archivalId, number, reason, archivedByUserId (null only for periods created by the migration), archivedAtUtc, unarchiveReason, unarchivedByUserId, unarchivedAtUtc }` (the three unarchive fields are null while the period is current).
  - `CaseLifecycleDto { status, archived, currentClosure (set only while the case is Closed), currentArchival, closures[] (oldest first, each with its reopening), archivals[] (oldest first) }`. Unpaginated per-case history (pilot scale); 404 for an unknown or foreign case.
- **Blocked while Closed or archived (409).** The shared `CaseService.EnsureMutable` (Closed -> `Closed cases cannot be changed; reopen the case first.`; archived -> `Archived cases cannot be changed; unarchive the case first.`) guards `PATCH .../requirements/{id}`, `POST .../supplier-request`, `POST /api/supplier-requests/{id}/regenerate`, every public token route (a revoked link answers 404 first), `POST .../documents`, `DELETE .../documents/{id}`, `POST .../geolocation`, `PUT .../dossier/lot`, `POST .../master-data/refresh`, `PUT .../applicability`, `PUT .../recipients`, `POST`/`DELETE .../evidence-links`, `POST .../reviews` and `PUT /api/shipments/{id}`; plus `close` on a Closed case and `close`, `reopen` and `archive` on an archived case. Reads, `GET .../export`, the reviewed export and `POST /api/supplier-requests/{id}/revoke` (which only reduces access) stay available. A rejected write records nothing.
- **Case details and list.** `GET /api/eudr-cases/{id}` returns `status` (a workflow status) plus `closure` (the current `CaseClosureDto`, only while Closed, else null) and `archive` (the current `CaseArchivalDto`, else null); `completedAtUtc` and `externalDdsReference` no longer exist. `GET /api/eudr-cases` items gain `archived` (boolean) and `closureOutcome` (the current closure's outcome while Closed, else null); archived cases are excluded unless `archived=only|include` is given (see "Shapes").
- **Dashboard.** `GET /api/dashboard` returns `{ total, activeOpen, activeOpenByStatus: { draft, waitingForSupplier, reviewNeeded, readyForExport }, activeClosed, activeClosedByOutcome: { externalDdsCompleted, outsideRegulatoryScope, unsupportedFlow }, archived }`. The three buckets are mutually exclusive and cover every case once: an archived case counts only under `archived` whatever its status, `total = activeOpen + activeClosed + archived`, and each breakdown sums to its bucket (for valid data: every Closed case has a closure). All counts come from one repeatable-read snapshot. `totalOpenCases` no longer exists.
- **Removed routes.** `POST /api/eudr-cases/{caseId}/complete` (404) and `DELETE /api/shipments/{id}` (405) no longer exist. `status=Completed` and `status=Archived` on the case list are 400.
- **Status codes.** 401 anonymous; 403 Member (before case and body); 404 unknown/foreign case; 400 body validation; 415 non-JSON body (after the state checks); 409 state preconditions, review or closure mismatch, used or stale review; 405 for other methods on these paths.

## External DDS records (manual external submission facts)

Internal, authenticated routes ([ADR 0011](adr/0011-external-dds-record-v1.md)); module `Endpoints/Cases/ExternalDdsEndpoints.cs`, service `Services/ExternalDdsService.cs`, records in `Contracts/ExternalDds.cs`, validator `CreateExternalDdsRecordValidator` in `Contracts/Validators.cs`, close gate `CaseClosurePolicy.ExternalDdsError`. The record states that the dossier version captured by one immutable Owner review was submitted to the EU Information System **outside Provena**. It is not an approval, EU acceptance, compliance or verification, and Provena makes no network call. Handoff for clients: [frontend handoff](frontend-handoffs/2026-10-external-dds-record.md).

| Route | Who | Success |
| --- | --- | --- |
| `GET /api/eudr-cases/{caseId}/external-dds` | any member | **200** `ExternalDdsRecordDto` (the current record) or **204** when none |
| `GET /api/eudr-cases/{caseId}/external-dds-history` | any member | **200** `ExternalDdsRecordDto[]`, newest first (highest `number`), unpaginated per-case history |
| `POST /api/eudr-cases/{caseId}/external-dds` | Owner | **201** `ExternalDdsRecordDto`, Location = `GET .../external-dds` |

- **Request** `{ expectedLatestExternalDdsRecordId?, reviewId, referenceNumber, verificationNumber, submittedAtUtc, receiptDocumentId?, replacementReason? }`; no `organizationId`. Numbers are trimmed, required, non-blank, at most 200 characters, and never interchangeable. `expectedLatestExternalDdsRecordId` is `null` for the first record and the exact current record id for a replacement.
- **Response** `ExternalDdsRecordDto { recordId, number, reviewId, referenceNumber, verificationNumber, submittedAtUtc, recordedByUserId, recordedAtUtc, receiptDocumentId, supersedesRecordId, replacementReason, supersededAtUtc, isCurrent }`.
- **Order of checks for POST (a contract).** Transaction; live Owner check (403 for a Member whatever the case id or body; the body is not read); unknown or foreign case 404; Closed or archived case 409 (`CaseService.EnsureMutable` messages); body: non-JSON 415, malformed JSON 400; validation 400 (`errors.ReviewId`, `ReferenceNumber`, `VerificationNumber`, `SubmittedAtUtc`, `ExpectedLatestExternalDdsRecordId`, `ReceiptDocumentId`, `ReplacementReason`); `submittedAtUtc` after now -> 400 `errors.SubmittedAtUtc`; optimistic check -> 409 `errors.reason = "ExternalDdsHistoryChanged"`; replacement without a non-blank reason, or a reason on the first record -> 400 `errors.ReplacementReason`; review rules (below); receipt rule -> 409 `ReceiptDocumentNotCurrent`; then the write. A rejected request writes nothing (no row, no supersession, no audit).
- **Review rules** (re-evaluated under the case lock): `reviewId` is not the latest review, or is unknown/foreign/absent (identical non-disclosing response) -> 409 `ReviewNotLatest`; decision is not `AcceptedAsCompleteUnderPolicy` -> 409 `ReviewNotAccepted`; `submittedAtUtc` earlier than that review's `ReviewedAtUtc` -> 400 `errors.SubmittedAtUtc` (equality is valid; no tolerance; UTC-normalised); the review is stale -> 409 `StaleReview` with `changedAreas`. Quantity reconciliation is **not** required to record.
- **Receipt** `receiptDocumentId`: must be a current (not withdrawn) document of the same case and tenant; withdrawn, unknown, other-case and other-tenant ids give the identical 409 `ReceiptDocumentNotCurrent`. A later withdrawal keeps the record and link.
- **Replacement.** Inserts the next `number`, sets `supersedesRecordId` to the previous current row, requires `replacementReason`, and sets the previous row's `supersededAtUtc` (the only update ever made to an existing row). Nothing is edited or deleted; it is not an EU-system amendment. Audit `ExternalDdsRecorded` or `ExternalDdsReplaced` carries ids only. Simultaneous first records give one 201 and one 409.
- **Sensitive value.** `verificationNumber` is returned only by these routes (and echoed nowhere else): not in case details/list, lifecycle, completeness, reviews, exports, ProblemDetails, audit text or logs.
- **Closing.** For `ExternalDdsCompleted` the close gate runs after the stale-review and quantity checks (see "Case lifecycle"); `CloseCaseInput.externalDdsReference` stays accepted but optional, non-authoritative, and must equal the current record's `referenceNumber` when supplied. `CaseClosure.externalDdsReference` is the only legacy field; `EudrCase` has none.
- **Status codes.** 401 anonymous; 403 Member on POST; 404 unknown/foreign case; 400/415 body; 409 state, concurrency, review, receipt; 405 for PUT/PATCH/DELETE.

## Post-completion concerns (concerns, corrective actions, notifications, resolution)

Internal, authenticated routes ([ADR 0012](adr/0012-post-completion-concerns-v1.md)); module `Endpoints/Cases/ConcernEndpoints.cs`, service `Services/ConcernService.cs`, records in `Contracts/Concerns.cs`, validators `CreateConcernValidator`, `RecordConcernActionValidator`, `RecordConcernNotificationValidator` and `ResolveConcernValidator` in `Contracts/Validators.cs`. A concern is a retained record about a Completed (`Closed`) or archived case; it never reopens the case and never changes its status, closure, reviews, freshness, fingerprint, External DDS record, quantities or supplier links. It is not a compliance, approval, recall-completion or regulatory-acceptance statement, and nothing is sent. Frontend handoff: [2026-10-post-completion-concerns](frontend-handoffs/2026-10-post-completion-concerns.md).

| Route | Who | Success |
| --- | --- | --- |
| `GET /api/eudr-cases/{caseId}/concerns` | any member | **200** `ConcernSummaryDto[]`, newest first (highest `number`), unpaginated per-case list |
| `POST /api/eudr-cases/{caseId}/concerns` | any member | **201** `ConcernDto`, Location = `GET .../concerns/{concernId}` |
| `GET /api/eudr-cases/{caseId}/concerns/{concernId}` | any member | **200** `ConcernDto` |
| `POST .../concerns/{concernId}/actions` | any member | **201** `ConcernActionDto`, Location = the concern |
| `POST .../concerns/{concernId}/notifications` | any member | **201** `ConcernNotificationDto`, Location = the concern |
| `POST .../concerns/{concernId}/resolution` | Owner | **201** `ConcernResolutionDto`, Location = the concern |

- **Requests** (no `organizationId`, `status` or `resolvedAtUtc`): `CreateConcernInput { category, summary, details, raisedAtUtc }`; `RecordConcernActionInput { description, performedAtUtc, evidenceDocumentId? }`; `RecordConcernNotificationInput { recipientId, channel, notifiedAtUtc, note?, evidenceDocumentId? }`; `ResolveConcernInput { outcome, rationale }`. Text is trimmed and required/non-blank (summary <= 200, details, description and rationale <= 4000, note <= 1000, a blank note becomes null); enums are strings and must be defined; the three instants are normalised to UTC and must not be in the future (no tolerance); a non-null empty Guid is 400.
- **Enums.** `category`: `NewInformation`, `SupplierNotification`, `AuthorityNotification`, `InternalFinding`, `Other`. `channel`: `Email`, `Phone`, `Letter`, `Portal`, `Other`. `outcome`: `CorrectiveActionCompleted`, `NoFurtherActionRequired` only (external escalation is an action and/or notification, never a resolution).
- **Responses.** `ConcernDto { concernId, number, category, summary, details, raisedAtUtc, recordedByUserId, recordedAtUtc, status (Open|Resolved, derived), actions, notifications, resolution }`; `ConcernSummaryDto { concernId, number, category, summary, raisedAtUtc, status, actionCount, notificationCount, resolvedAtUtc }`; `ConcernActionDto { actionId, description, performedAtUtc, recordedByUserId, recordedAtUtc, evidenceDocumentId }`; `ConcernNotificationDto { notificationId, recipient { recipientId, name, postalAddress, email }, channel, notifiedAtUtc, note, evidenceDocumentId, recordedByUserId, recordedAtUtc }`; `ConcernResolutionDto { resolutionId, outcome, rationale, resolvedByUserId, resolvedAtUtc }`. Actions are oldest first by `performedAtUtc`, notifications by `notifiedAtUtc`.
- **Order of checks (a contract).** Transaction; for the resolution only, the live Owner check (403 for a Member whatever the case, concern or body; the body is not read); tenant-scoped case lock (unknown or foreign case 404); concern lookup within the case (404); for concern creation only, the case must be `Closed` or archived (409 `CaseNotCompleted`); body: non-JSON 415, malformed JSON 400; validation 400 (`errors.<Property>`) including the future-instant rules; then the state rules: concern already resolved -> 409 `ConcernResolved`, notification recipient not a recipient of this case -> 409 `RecipientNotFound`, evidence not a current document of this case -> 409 `EvidenceDocumentNotCurrent`; then the write. Unknown, other-tenant, other-case and (for evidence) withdrawn ids answer identically.
- **Case state.** Only creation depends on the case being Completed or archived. For an existing concern, actions and notifications depend only on the concern not being resolved, not on re-checking the case status; reads are always allowed. The case is never modified.
- **Recipient.** `recipientId` is the id of a `CaseRecipient` (the `recipients[].id` of the recipient statement routes) of any statement version, current or superseded, of the same case. The notification stores only that id; the response joins the immutable row's name, address and e-mail.
- **Evidence.** `evidenceDocumentId` must be a current document of the same case when linked. A later withdrawal keeps the link and the read.
- **Resolution.** One per concern, Owner only; the server sets `resolvedAtUtc`. Afterwards no action, notification or second resolution (409 `ConcernResolved`); the concern stays readable and is never reopened; a later issue is a new concern.
- **Concurrency.** Writes run under the case lock; two simultaneous resolutions give one 201 and one 409; an action or notification racing a resolution is serialized so none is written after it.
- **Audit.** `ConcernRecorded`, `ConcernActionRecorded`, `ConcernNotificationRecorded`, `ConcernResolved`: ids and numbers only, never the text fields or recipient data.
- **Status codes.** 401 anonymous; 403 Member on the resolution; 404 unknown/foreign case or concern; 400/415 body; 409 state; 405 for PUT/PATCH/DELETE.

## Errors

`Common/ExceptionHandler.cs` returns ProblemDetails with status/title/detail/type and traceId. FluentValidation errors are grouped by property into `errors`; ApiException may supply another errors shape. Known status mappings: 400 validation; 401 authentication; 403 membership check in Me; 404 unavailable records/tokens; 409 workflow or selected PostgreSQL conflicts; 413 file size; 429 rate limiting; generic 500 for unexpected errors. Parameter-binding failures (`RouteHandlerOptions.ThrowOnBadRequest`) also pass through this handler: 400 with title "Validation failed" and a framework detail message but no per-field `errors`, or 415 for a non-JSON/non-form content type, including a request with neither body nor Content-Type where a JSON body is required (`WithRequiredJsonBodyContentTypeCheck`). Auth (401/403), unmatched route (404), wrong method (405) and rate-limit (429) responses come from status-code pages or the limiter, so their details/extension shapes differ; do not assume every failure passed through this handler. ProblemDetails customization clears Instance to avoid token-bearing URLs. There is no universal error-code enum.

## Uploads and supplier capability

Multipart field is `file`; internal documents additionally accept form `category`. Upload route groups (internal case files, imports, public supplier) apply `WithUploadLimits()`: 21 MiB request and multipart limits; FileValidationService imposes configured 1–20 MiB per file (default 20). [SECURITY](SECURITY.md) describes validation limitations and capability lifecycle. [EUDR_DOMAIN](EUDR_DOMAIN.md) owns evidence/review effects; do not duplicate transition logic in endpoint handlers.

Public `PUT /public/supplier-requests/{token}/details` validates `confirmedQuantity` as greater than 0, below 1e14 and at most 6 decimal places (`400` ProblemDetails with `errors.ConfirmedQuantity` otherwise, so an exact value is never silently rounded in storage). A confirmed quantity that differs from the shipment quantity is accepted (`204`): submission is not acceptance, and the difference is reported by the completeness `quantityReconciliation` ([ADR 0010](adr/0010-quantity-reconciliation-v1.md)). The quantity has no unit field and is taken to be in the shipment unit.

## CSV imports

UTF-8 comma-separated input, exact header names and order, trimmed fields, <=10,000 data rows and normal file limits. No Excel import despite accepting Excel as supporting documents.

| Kind | Exact header |
| --- | --- |
| suppliers | `externalReference,name,email,contactPerson,countryCode` |
| products | `externalReference,name,cnCode,commodityType,description` |
| shipments | `referenceNumber,supplierExternalReference,productExternalReference,quantity,unit,originCountryCode` |

Quantities use invariant decimal parsing; enum names are case-sensitive. The current Enum.TryParse + IsDefined combination also accepts defined numeric enum strings; do not claim names-only CSV validation. Shipment references resolve via ExternalReference within the tenant-filtered sets. The model and initial SQL have per-organization partial unique indexes for non-null supplier/product external references.

Rows create new records; this is not upsert. Invalid file/header/parser failures abort before writes. After parsing, valid rows persist independently; caught validation/API/DbUpdate failures are reported with row index `i+2` (logical data row plus header, not physical lines for multiline CSV). Result: totalRows/imported/failed/errors. No whole-file rollback, idempotency key or background queue. The declared external-reference indexes prevent duplicate non-null values within an organization when the supplied schema is applied; migrations and live schema still require runtime verification.

## Export contract

Every case can be exported in any state (Closed and archived cases included). Package root `case-{safeReference}/` contains manifest.json, UTF-8 BOM summary.csv, documents named with ID + sanitized filename, and geolocation/original.geojson when present, plus `plots/{plotRevisionId:N}.geojson` (normalized stored geometry, once per distinct revision) for every plot revision pinned by the **current** dossier lot. Manifest includes organization, shipment, supplier, product, supplier submission, requirements, document/geo metadata, status/reference/timestamps and audit events, plus an operational-only notice, `dossier` (the current `CaseDossierDto` shape including production periods, or null when none exists), `dossierScope` ("Current operator dossier lot at export time; not a reviewed dossier snapshot and not a completeness or compliance determination.") and `retainedNotIncluded.supersededLotVersions` (superseded lot versions are counted, not exported). `evidenceScope` and the `summary.csv` header are unchanged. Tokens/storage keys are not intentionally projected. CSV values are quoted and leading formula characters are prefixed with an apostrophe. ZIP creation records CaseExported, so GET has a database side effect. Export is not a DDS message or external submission. The manifest also carries `completeness` (the current `CompletenessDto`, computed inside the same case-locked transaction), `latestReview` (the same object as `completeness.latestReview`, or `null` before the first review) and `reviewScope` ("Working-current export. Not the reviewed record; use the review export for what was reviewed."); the existing members, `evidenceScope`, `dossierScope`, `summary.csv` and the package layout are unchanged, except that the manifest carries `lifecycle` (the same object as `GET .../lifecycle`: closures with their reviews and reopenings, and the archive periods, read under the same case lock) and no longer carries `externalDdsReference` or `completedAtUtc`; `status` is the workflow status (`Closed`, never `Completed`/`Archived`). This working export is not a reviewed record.

## Compatibility rule

Breaking change recorded: `GET /api/suppliers`, `/api/products` and `/api/shipments` returned a bare JSON array and now return `PageResult<T>` with default page size 25. Clients must read `items` and page through `totalCount`; no frontend is supplied, so client impact is untested.

Before changing an endpoint, inspect DTOs, service projection, tests and `scripts/smoke.py`. No frontend is supplied: do not claim frontend compatibility was tested. Treat renames, enum changes, nullability, status codes, pagination, CSV headers and ZIP manifest fields as contract changes. Prefer explicit additive evolution where safe; ask the owner about breaking changes and record migration/rollout expectations. Add HTTP assertions for externally visible changes, including negative access paths.
