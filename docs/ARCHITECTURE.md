# Actual architecture

## Observed source structure

A single ASP.NET Core application contains Minimal API endpoint modules, record contracts, services, mutable domain entities and infrastructure adapters. Domain folders organize code but share the same namespace and assembly. Services call EF directly; no repository layer, mediator, aggregate implementation or event bus is supplied. `Data/AppDbContext.cs` derives from IdentityDbContext and contains inline EF mappings, tenant query filters and tracked-write guards; [DATABASE](DATABASE.md) owns their scope.

HTTP → middleware/auth → Minimal API parameter binding → endpoint handler → service validation/orchestration → EF and optional file/email I/O → `TypedResults` with a DTO/entity/anonymous response. Read methods frequently use `AsNoTracking`. FluentValidation is invoked explicitly by services, not through an endpoint filter or automatic pipeline.

## HTTP layer convention

Owner decision recorded in [ADR 0003](adr/0003-minimal-api-http-layer.md):
- MVC Controllers are not used. Endpoints live in `src/Provena.Api/Endpoints/<Feature>/`, one static `Map<Feature>Endpoints` module per route group, with named private static handlers.
- `Endpoints/ProvenaEndpoints.cs` exposes the only registration call, `app.MapProvenaEndpoints()`. Program.cs maps no individual endpoints.
- Internal groups nest under the authorized `/api` group. Public capability routes have their own anonymous, rate-limited group.
- Handlers only bind input, call one scoped service method and map the result. Validation, transactions, locks, tenant checks and status transitions stay in services.
- Shared HTTP conventions (upload limits, lenient query/form enum parsing) live in `Endpoints/EndpointConventions.cs`.

## Composition and lifetime

`Program.cs` registers `AppDbContext` via `AddDbContext` (scoped default); `TenantContext`, orchestration/auth/audit/seeder services and `IEmailSender` are scoped. Token generation, file/geometry validation and `IFileStorage` are singleton. Do not add request/tenant state to singleton services. Identity uses `ApplicationUser`, Guid roles, EF stores and SignInManager. Existing adapters are `LocalFileStorage` and `DevelopmentEmailSender` in every environment.

Middleware: exception handler → status code pages → production HSTS/HTTPS redirect → no-store/nosniff/no-referrer headers → routing → CORS → authentication → authorization → rate limiter → Minimal API endpoints (`MapProvenaEndpoints`). HTTP JSON options (string enums, max depth 32) and `RouteHandlerOptions.ThrowOnBadRequest` are configured in Program.cs. OpenAPI/Scalar are mapped only in Development/Testing. Startup validates selected configuration; [DEPLOYMENT](DEPLOYMENT.md) owns the settings.

## Transactions and consistency

Registration explicitly transacts user, organization and membership creation. New shipments transact shipment, case, checklist and audit writes. Existing case operations commonly begin a transaction then call `CaseService.Lock`, a PostgreSQL `SELECT ... FOR UPDATE` with explicit case and organization predicates. Preserve the transaction around the lock. Public requests resolve the capability, acquire this case lock, then recheck hash/revocation/expiry to address concurrent rotation/revocation.

Review, supplier writes, uploads, deletion, request lifecycle and export use case locking. Export adds an audit record, gathers details and copies file bytes into a disk-backed ZIP while holding the transaction; this can hold a lock for a long export. Normal Details uses multiple queries without the same snapshot/locking guarantee. A case dossier lot save (`CaseDossierService.SaveLot`) takes the case lock first, then locks the referenced producers and plots `FOR SHARE` (each ordered by id, organization-scoped) so the active-state decision is serialized with concurrent deactivation, supersedes the current lot and saves before inserting its successor; a shipment update checks dossier existence after the same case lock, so it serializes with dossier saves. Catalog saves do not acquire case locks. Do not claim that all data associated with a case is frozen or that every read is an atomic snapshot. Working-fact writes (`CaseMasterDataService.Refresh`, applicability, recipients and evidence links) take the case lock first, then check the case is editable, then validate the body; a refresh additionally locks the operator profile, the shipment supplier and the shipment product `FOR SHARE` in that order (the shipment is read under the case lock), and `OperatorProfileService.Save` locks its own row `FOR UPDATE`. `CompletenessService.Get` reads the completeness model in a repeatable-read snapshot without locks or writes (the working export computes it inside its case-locked transaction); `DossierFactsBuilder` (collect case-owned facts), `CompletenessEvaluator` (pure policy v1 rules) and `DossierFingerprint` (pure canonical hash) are deliberately separate and are reused by ReviewService under its fixed lock order. `ReviewService.Create` has a fixed order that must not be rearranged: transaction, live Owner check (403, before any case lookup or body parsing), tenant-scoped case lock `FOR UPDATE` (404), `EnsureEditable` (409), body validation (400), read the shipment, `FOR SHARE` locks on the operator profile, the shipment supplier and the shipment product (the master-data refresh order), build facts and evaluate, resolve the latest review by revision number, compare `expectedFingerprint` and `expectedLatestReviewId` (409), decision preconditions (409), next revision number, insert revision + pins + record, audit, `UpdatedAtUtc`, commit. The snapshot is hybrid: immutable rows are pinned by composite FKs and the mutable context is copied into a typed `SnapshotJson`; freshness is derived on read by fingerprinting the current facts with the review's stored `FingerprintVersion` (old versions stay executable), so a review is never mutated and never recomputed under a newer policy. The reviewed export and review detail read only the stored revision and take no case lock.

File storage and database are not one transaction. Upload deletes its own new bytes only when the failure happened before the commit was attempted (a `commitAttempted` flag); once `CommitAsync` has been called, even if it throws, the bytes are kept because the commit outcome may be ambiguous and orphaned bytes are safer than deleting committed evidence. Committed evidence bytes are never deleted: document DELETE withdraws the row, and geometry replacement supersedes the previous row, keeping both files ([ADR 0005](adr/0005-retained-evidence-append-only-rows.md)). A failed upload can still leave orphaned bytes if rollback cleanup itself fails; there is no durable cleanup queue, orphan sweep, archival tier or retention schedule. Email runs after request creation commits; failures would not roll back the request. Current email is a logging stub, so no delivery retry exists.

## Error, audit and observability conventions

`ApiException` represents expected HTTP failures. `ExceptionHandler` maps validation to 400, concurrency and selected PostgreSQL constraint errors to 409, and unexpected errors to generic 500. It logs type/status/trace ID without exception text. [API](API.md) owns response details.

`AuditService.Add` adds an entity to the current DbContext and logs event/case/organization IDs; callers save it. Descriptions are usually concise and IDs-based. `AppDbContext.SaveChangesAsync(CancellationToken)` rejects tracked AuditEvent modification/deletion. No database trigger or restricted audit-table grants are supplied; other save overloads and direct/bulk writes are outside that guard. This is application-level append-only enforcement, not a tamper-proof audit guarantee. The same override also enforces append-only retained evidence rows (see [DATABASE](DATABASE.md)).

No hosted/background service, scheduler, message broker, external HTTP integration, distributed cache or tracing backend is supplied. Expiry is checked at request time. Logging uses ASP.NET logging; the development email stub logs the recipient email. [SECURITY](SECURITY.md) owns redaction and deployment boundaries.

## Project rules / recommendations

Keep the existing service architecture for routine features. Preserve cancellation and transaction ordering. Use DTO projections at public boundaries. Do not introduce generic repositories or additional assemblies solely to match a theoretical architecture. A substantial boundary change needs a concrete problem, plan and owner decision. Durable current choices and target decisions are recorded selectively in [ADRs](adr/README.md); source remains the evidence for behaviour.
