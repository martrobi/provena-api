# Persistence and schema workflow

## Source of truth

The second archive includes `src/Provena.Api/Data/AppDbContext.cs`, `DesignTimeFactory.cs`, `Migrations/20261010180000_InitialCreate.cs` and `Migrations/AppDbContextModelSnapshot.cs`. The earlier missing-source finding is resolved. This document describes declared mappings and SQL, not an inspected live database or an executed migration.

AppDbContext derives from `IdentityDbContext<ApplicationUser, IdentityRole<Guid>, Guid>`. OnModelCreating calls the Identity base configuration, then defines application mappings inline. PostgreSQL via Npgsql is the provider; compose/tests use PostgreSQL 17. There is no repository layer, separate mapping assembly or PostGIS column. NetTopologySuite validates geometry in application memory.

## IDs, columns, timestamps and concurrency

- Entity IDs are Guid values initialized with Guid.NewGuid; SQL uses uuid. Each tenant type has primary key Id and alternate key `(OrganizationId, Id)`; `HasBaseType(null)` maps each independently rather than one inheritance table.
- Entity initializers set CreatedAtUtc/UpdatedAtUtc using UTC DateTimeOffset; SQL uses timestamp with time zone. The overridden `SaveChangesAsync(CancellationToken)` updates UpdatedAtUtc on modified Entity instances. It does not make CreatedAtUtc immutable.
- ApplicationUser and OrganizationUser have timestamp properties but do not inherit Entity; this override does not maintain their UpdatedAtUtc. No timestamp trigger is supplied.
- Shipment.Quantity and SupplierSubmission.ConfirmedQuantity use numeric(20,6). DateOnly fields use date. Domain enums persist as integers; preserve numeric meanings when adding/reordering members. JSON uses names independently of SQL storage. `EudrCaseStatus` is `Draft` 0, `WaitingForSupplier` 1, `ReviewNeeded` 2, `ReadyForExport` 3, `Closed` 4 (the former `Completed` value; the former `Archived` value 5 is unused and archive is a separate table).
- GeoSubmission.RawGeoJson and AuditEvent.MetadataJson use jsonb. Other strings without a specific maximum default to 4000 characters, including inherited Identity strings without an existing configured maximum. Exceptions include Identity name/email limits, user first/last name (100), organization name (200), OIB (11), and token hash (64).
- API validators are often stricter than database columns (e.g. supplier name max 200 vs varchar(4000)); database constraints do not duplicate every input rule. Positive quantities, country codes and enum eligibility are validated in application code, not SQL CHECK constraints here.
- The snapshot marks Identity user/role ConcurrencyStamp as concurrency tokens. Tenant business entities have no configured row-version/concurrency token; case operations instead use explicit PostgreSQL row locks where documented in ARCHITECTURE.

## Tenant and audit guards

ConfigureTenant is applied to all twenty-seven tenant types: Supplier, Product, Shipment, EudrCase, EudrRequirement, SupplierRequest, SupplierSubmission, CaseDocument, GeoSubmission, AuditEvent, Producer, ProductionPlot, PlotRevision, CaseDossier, CaseLot, LotContribution, ContributionPlot, OperatorProfile, CaseMasterDataVersion, CaseApplicability, CaseRecipientStatement, CaseRecipient, CaseEvidenceLink, CaseRevision, CaseRevisionDocument, CaseRevisionEvidenceLink and ReviewRecord. Each gets an organization FK and query filter `OrganizationId == TenantId`; TenantId reads the scoped TenantContext. Organization, OrganizationUser and Identity sets are not globally tenant-filtered: callers must scope those queries deliberately.

`SaveChangesAsync(CancellationToken)` inspects tracked Entity instances. For added/modified/deleted TenantEntity rows it rejects an empty current tenant or a current OrganizationId different from the tenant; for modifications/deletions the original OrganizationId must also match. This prevents simply reassigning a foreign tracked row to the current tenant through this save path. It rejects tracked AuditEvent modifications/deletions before saving. Services stamp OrganizationId explicitly; the context does not silently fill it in.

**Retained evidence guard.** The same override applies to `CaseDocument`, `GeoSubmission` and `SupplierSubmission`: `Deleted` is always rejected, and `Modified` is allowed only as one retirement transition from an unretired row: the marker (`WithdrawnAtUtc` or `SupersededAtUtc`) must change from null, `WithdrawnByUserId` may change only in that same transition (its original must also be null), and `UpdatedAtUtc` is tolerated only alongside the marker (on its own it throws). Un-retiring, re-timestamping, filling the withdrawal actor later, or editing stored values/keys throws `InvalidOperationException`. Use `Data/RetainedEvidence.cs` `Current()` for "current" queries instead of a global query filter (a filter would push history reads towards `IgnoreQueryFilters`). A supersede is saved before the replacement row is added, inside the case-locked transaction, because EF cannot order the writes around the filtered unique index.

**Production provenance guard.** `PlotRevision` is routed through the same retained-evidence path (marker `SupersededAtUtc`, no companions): immutable after insert except for the one-way supersede, never deleted. `Producer` and `ProductionPlot` are identities: `Deleted` is always rejected ("deactivate them"), and for `ProductionPlot` a modified `ProducerId` is rejected (a producer or tenure change is a new plot). Their descriptive fields and `IsActive` stay editable. `Current()` also exists for `PlotRevision` (`SupersededAtUtc IS NULL`). As above, the guard is application-level only.

**Case dossier guard.** `CaseLot` joins the retained-evidence retirement map (marker `SupersededAtUtc`, no companions): its facts (`Number`, `LotReference`, `Quantity`, `Unit`, `Note`, `CreatedByUserId`, `CaseDossierId`) are immutable and only the one-way null -> value supersede is allowed; deletes are rejected. `CaseDossier`, `LotContribution` and `ContributionPlot` are fully immutable: any `Modified` (every column, including `EudrCaseId`, `CreatedByUserId` and `UpdatedAtUtc`) or `Deleted` entry throws "Case dossier rows are immutable; save a new lot version." `Current()` exists for `CaseLot` (`SupersededAtUtc IS NULL`). Application-level only, like the guards above: other save overloads, bulk writes and raw SQL bypass it.

**Completeness facts guard.** `CaseMasterDataVersion`, `CaseApplicability` and `CaseRecipientStatement` join the retained-evidence retirement map (marker `SupersededAtUtc`, no companions) and `CaseEvidenceLink` joins it with marker `WithdrawnAtUtc` and companion `WithdrawnByUserId`: every fact column is immutable, only the one-way null -> value retirement is allowed, deletes are rejected. `CaseRecipient` is fully immutable (any `Modified` or `Deleted` entry throws "Case recipients are immutable; save a new recipient statement version."). `OperatorProfile` is mutable catalogue-like data, but a `Deleted` entry throws. `Current()` exists for the four retirable types (`SupersededAtUtc IS NULL`, `WithdrawnAtUtc IS NULL` for links). Application-level only, like the guards above: other save overloads, bulk writes and raw SQL bypass it, so the unique indexes and Restrict foreign keys below are the database backstop.

**Review history guard.** `CaseRevision`, `CaseRevisionDocument`, `CaseRevisionEvidenceLink` and `ReviewRecord` are fully immutable: any `Modified` (every column, including `UpdatedAtUtc`) or `Deleted` entry throws "Review history is immutable; record a new review." This sits beside, and does not weaken, the retirement guards of the rows a revision pins (a pinned document can still be withdrawn, a pinned lot superseded: the revision keeps its pins). Application-level only, like the guards above: other save overloads, bulk writes and raw SQL bypass it, and the Restrict foreign keys, the unique indexes and the CHECK are the database backstop.

**Case lifecycle guard.** `CaseClosure` and `CaseReopening` are fully immutable: any `Modified` (every column, including `UpdatedAtUtc`) or `Deleted` entry throws "Case lifecycle history is immutable; record a new closure or reopening." `CaseArchival` joins the retirement map (marker `UnarchivedAtUtc`, companions `UnarchivedByUserId` and `UnarchiveReason`): the archive facts are immutable, the only allowed update is the one-way null -> value unarchive and deletes are rejected (the standard retained-evidence messages). `Current()` exists for `CaseArchival` (`UnarchivedAtUtc IS NULL`). Application-level only, like the guards above: other save overloads, bulk writes and raw SQL bypass it, and the unique indexes and Restrict foreign keys below are the database backstop.

**Scope matters:** only this async overload is overridden. Synchronous SaveChanges, the async bool overload, ExecuteUpdate/ExecuteDelete and raw SQL do not run this custom guard. Bulk operations may still have query filters unless bypassed, but do not receive the tracked-write/audit/timestamp checks. No database row-level-security policy, audit trigger or restricted audit-table grants are supplied. Do not describe these controls as universal database immutability. Ordinary application saves currently call the guarded overload; expiry integration tests deliberately use IgnoreQueryFilters + ExecuteUpdateAsync.

All application relationships above use DeleteBehavior.Restrict / SQL ON DELETE RESTRICT. Identity claim/login/role/token relationships use cascade as declared by Identity's model and SQL. Composite case/foreign-reference indexes support lookups. Unique constraints enforce **at most one**, not that a related record necessarily exists; shipment service creates its case/checklist transactionally.

The request partial index counts expired or completed requests until revoked; this matches Create's refusal when any non-revoked request exists. It does not enforce expiry or delivery semantics.

The `CaseDossier` migration's new alternate keys exist only to support the dossier chain FKs: `ProductionPlots (OrganizationId, ProducerId, Id)` and `PlotRevisions (OrganizationId, ProductionPlotId, Id)`. "Exactly one current lot once a dossier exists" is not a database constraint (the unique index allows none): the first lot save creates the dossier and lot 1 in one transaction, and a supersede is saved before the successor is inserted (a `CaseDossierService` obligation). `CaseDossiers.CreatedByUserId` and `CaseLots.CreatedByUserId` have no FK.

"At least one current revision" is not a database constraint: a plot is created together with revision 1, and a supersede happens in the same transaction as the insert of its successor (a `ProvenanceService` obligation). `Producers.CreatedByUserId`, `ProductionPlots.CreatedByUserId` and `PlotRevisions.CreatedByUserId` have no FK, like the other attribution ids.

No FK is declared for Documents/Geolocations/AuditEvents.SupplierRequestId, AuditEvents.ActorUserId or Requirements.ReviewedByUserId. Request.SupplierId and request.CaseId are each tenant-consistent, but the schema does not prove the supplier equals that case's shipment supplier. Service flow establishes these associations today; future alternate write paths must not assume database enforcement of them.

## Deletion behaviour

Unused supplier/product rows are removed; shipment references cause a service 409 and declared FK restrictions protect referenced rows. There is no shipment DELETE route: a case is archived through the lifecycle (a `CaseArchival` row; evidence retained, supplier requests revoked, the workflow status untouched). Evidence is never physically deleted or overwritten ([ADR 0005](adr/0005-retained-evidence-append-only-rows.md)): document DELETE sets `WithdrawnAtUtc`/`WithdrawnByUserId`; a geometry upload or supplier details save inserts a new row and sets `SupersededAtUtc` on the previous current row. Rows and stored bytes stay (`IFileStorage.DeleteAsync` is only used to clean up uncommitted bytes after a failed upload). Legacy rows that predate this change are simply current, with null actor/request metadata; destroyed earlier versions are not reconstructed. There is no erasure/disposal path and no retention schedule (open legal item); capacity of the unbounded retained history is deferred. Producers, production plots and plot revisions are never physically deleted ([ADR 0006](adr/0006-production-provenance-plot-revisions.md)): identities are deactivated (`IsActive=false`), revisions are superseded, and Restrict FKs are the database backstop for later references. Case dossiers, lot versions, contributions and plot links are never deleted or modified (lot versions are only superseded; Restrict FKs are the database backstop); [ADR 0007](adr/0007-case-dossier-lot-attribution.md). No general soft-delete column exists for other entities. [EUDR_DOMAIN](EUDR_DOMAIN.md) owns closed/archived-state exceptions.

## Migration history and the frozen initial target model

InitialCreate.Up/Down use embedded raw PostgreSQL SQL. Down drops all application/Identity tables with CASCADE: this is destructive and not a safe production rollback strategy.

InitialCreate's target model lives in its own file, `Data/Migrations/InitialCreate.TargetModel.cs` (a partial of the migration class; deliberately not named `.Designer.cs`, which the compiler treats as auto-generated and rejects nullable annotations in). It is a frozen copy of the original model and is independent of `AppDbContextModelSnapshot`, the only migration file EF rewrites when a migration is added. Never edit or regenerate it; a new migration gets its own target model from `dotnet ef migrations add`. Do not regenerate the initial migration over existing data.

`MigrationTests` (integration, own disposable PostgreSQL container) checks that the frozen model still describes the initial 19 tables, that a clean database migrates to the current snapshot, and that a database at the InitialCreate schema with a row upgrades to the latest migration keeping the row. The integration fixture's HasPendingModelChanges assertion checks current model vs snapshot, not whether hand-authored migration SQL matches either. Static review confirms major declared relationships/types/indexes; it does not prove complete model/DDL equivalence.

`RetainedEvidence` (20261012225511) adds nullable columns (`Documents`: `UploadedByUserId`, `WithdrawnAtUtc`, `WithdrawnByUserId`; `Geolocations`: `UploadedByUserId`, `SupersededAtUtc`; `Submissions`: `SupplierRequestId`, `SupersededAtUtc`) and replaces the two full unique indexes with partial unique ones of the same names. No backfill. User/request ids have no FK, like `ReviewedByUserId`. **Down caveat:** Down starts with a `DO $$` guard that raises `Retained evidence versions exist; rollback would destroy history` if any case has more than one geolocation/submission row, any row is superseded, or any document is withdrawn; only then does it drop the columns and restore the full unique indexes. Rollback is therefore only possible before retained versions exist. `MigrationTests` covers the partial indexes, upgrade with rows, the second-current-row violation, the guard refusal (schema and rows intact) and a clean Down. The snapshot was patched by hand in its existing compact format (EF regenerates it in the standard format); `HasPendingModelChanges` is asserted by the tests.

`ProductionProvenance` (20261012234200) is purely additive: it creates `Producers`, `ProductionPlots` and `PlotRevisions` with the keys, composite FKs and indexes above. No backfill (existing `Geolocations` rows are not converted to plots) and no change to existing tables. **Down caveat:** Down starts with a `DO $$` guard that raises `Production provenance records exist; rollback would destroy history` if any row exists in the three tables; only then does it drop `PlotRevisions`, `ProductionPlots`, `Producers`. Rollback is therefore only possible before any provenance data exists. `MigrationTests` covers the tables/indexes/composite FKs on a clean database, upgrade from `RetainedEvidence` with seeded rows (kept; provenance tables empty), the second-current-revision and duplicate-number violations, and the guard refusal (schema and rows intact) and clean Down. Its snapshot entries were hand-patched in the compact format; `HasPendingModelChanges` is asserted by the tests and the integration fixture.

`CaseDossier` (20261013004014) is purely additive: it creates `CaseDossiers`, `CaseLots`, `LotContributions` and `ContributionPlots` with the keys, composite FKs and (partial) unique indexes above, and adds only the two alternate keys to `ProductionPlots` and `PlotRevisions` (the existing redundant FK indexes on those tables are deliberately kept in the model so nothing is dropped). No backfill and no fabrication: legacy cases have no dossier, and nothing is derived from `Shipments`, `Submissions` or `Geolocations`. **Down caveat:** Down starts with a `DO $$` guard that raises `Case dossier records exist; rollback would destroy history` if any row exists in the four tables; only then does it drop `ContributionPlots`, `LotContributions`, `CaseLots`, `CaseDossiers` and the two alternate keys. `MigrationTests` covers the tables, period columns, indexes (including the `LotReference` partial filter), keys and composite FKs on a clean database, upgrade from `ProductionProvenance` with seeded rows (kept; dossier tables empty), the index/FK violations, the guard refusal (schema and rows intact) and a clean Down. Its snapshot entries were hand-patched in the compact format; `HasPendingModelChanges` is asserted.

`CompletenessFacts` (20261013213911) is purely additive: it creates `OperatorProfiles`, `CaseMasterDataVersions`, `CaseApplicabilities`, `CaseRecipientStatements`, `CaseRecipients` and `CaseEvidenceLinks` with the keys, composite FKs and (partial) unique indexes above, adds nullable `Suppliers.PostalAddress` and the `Documents (OrganizationId, EudrCaseId, Id)` alternate key (the existing `IX_Documents_OrganizationId_EudrCaseId` FK index is deliberately kept in the model so nothing is dropped). No backfill and no fabrication: legacy cases have no copy, applicability, recipients or links, and no supplier gets a postal address. **Down caveat:** Down starts with a `DO $$` guard that raises `Completeness fact records exist; rollback would destroy history` if any of the six tables has a row **or** any supplier has a non-null `PostalAddress`; only then does it drop the tables (children before parents), the `Documents` alternate key and the column. `MigrationTests` covers the tables, columns, indexes, alternate key and composite FKs on a clean database, upgrade from `CaseDossier` with seeded rows (all kept, new tables empty, no postal address), the guard refusal for each of the seven categories (schema and rows intact) and a clean Down that drops only these objects.

`ReviewedDossierHistory` (20261013224510) is purely additive: it creates `CaseRevisions`, `CaseRevisionDocuments`, `CaseRevisionEvidenceLinks` and `ReviewRecords` with the keys, composite Restrict FKs, `CK_CaseRevisions_DossierLotPair` and indexes above, and adds only alternate keys to existing tables: `CaseDossiers (OrganizationId, EudrCaseId, Id)`, `CaseLots (OrganizationId, CaseDossierId, Id)` and `(OrganizationId, EudrCaseId, Id)` on `Geolocations`, `Submissions`, `CaseApplicabilities`, `CaseRecipientStatements`, `CaseEvidenceLinks` and `CaseMasterDataVersions`. The FK-supporting `(OrganizationId, EudrCaseId)` / `(OrganizationId, CaseDossierId)` indexes those keys would make redundant are kept in the model, so nothing is dropped and no existing table gets a new index. No backfill and no fabrication: legacy and existing cases have no revision, review, reviewer or approval. **Down caveat:** Down starts with a `DO $$` guard that raises `Review history records exist; rollback would destroy history` if any row exists in the four tables; only then does it drop the pin tables, `ReviewRecords`, `CaseRevisions` and the eight alternate keys. `MigrationTests` covers the tables, `jsonb` columns, the CHECK, index uniqueness (including the non-unique timestamp index), the alternate keys and Restrict FKs on a clean database, upgrade from `CompletenessFacts` with seeded rows (all kept, review tables empty), the guard refusal for each of the four tables (schema and rows intact) and a clean Down that drops only these objects.

`CaseLifecycleV2` (20261015014806) is **not purely additive**: it creates `CaseClosures`, `CaseReopenings` and `CaseArchivals` with the keys, composite Restrict FKs and (partial) unique indexes above, adds the alternate key `AK_ReviewRecords_OrganizationId_EudrCaseId_Id` (the principal side of the closure's review FK; it also serves the `(OrganizationId, EudrCaseId)` prefix, so no extra index was added) and **drops `Cases.CompletedAtUtc` and `Cases.ExternalDdsReference`** after converting legacy data. The `EudrCaseStatus` integers are kept: `Completed` (4) was renamed `Closed`, and value 5 (`Archived`) no longer exists, so both legacy values are converted by `migrationBuilder.Sql` placed after the new tables exist and before the columns are dropped, in this order because each step reads what the next one changes:
1. *Legacy completion evidence.* For every case with `Status = 4` or a non-null `CompletedAtUtc` (a Completed case, or one completed and later archived) one System audit event `LegacyCompletionInvalidatedByMigration` is inserted (`ActorType` 2, no actor). Its `MetadataJson` keeps `legacyStatus` (`Completed` or `Archived`), `legacyCompletedAtUtc` and `legacyExternalDdsReference` (null when absent), so the old values survive the column drop. **No `CaseClosure` and no `CaseReopening` is invented:** a v2 closure needs a Current Owner review that legacy completions never had, and no Owner reopened anything.
2. *Legacy archive.* Every case with `Status = 5` gets one `CaseArchival` (`Number` 1, `ArchivedAtUtc` = the case's `UpdatedAtUtc`, `ArchivedByUserId` null, `Reason` `Archived before case lifecycle v2.`, current period).
3. *Status.* Every case with `Status` 4 or 5 is recalculated with one SQL `CASE` that mirrors `EudrCaseStatusService.CalculateOpen` (no sent request -> 0 `Draft`; a required requirement `Missing` -> 1; any `Submitted`/`Rejected` -> 2; all required `Accepted`/`NotRequired` -> 3; otherwise 1). `InternalReviewCompletedAtUtc` becomes `COALESCE(existing, now())` for status 3 and null otherwise, as `Recalculate` would.

Cases in the open statuses 0-3 are untouched. **Down** starts with a `DO $$` guard that raises `Case lifecycle records exist; rollback would destroy history` if any of the three tables has a row; otherwise it drops the tables and the alternate key and re-adds the two legacy columns **empty** (nullable; no reverse data conversion). Only the audit events keep the old values. The model snapshot was produced by `dotnet ef migrations add` and is **not hand-patched** (EF rewrote it from the earlier compact format to its standard format, hence the large diff); `HasPendingModelChanges` is asserted by the tests. `MigrationTests` covers the tables, columns, dropped legacy columns, unique/partial indexes, alternate keys and Restrict foreign keys on a clean database, an upgrade from `ReviewedDossierHistory` with five seeded legacy cases (open, Completed with and without a sent request, Archived never completed, Completed then Archived: statuses, no closures or reopenings, archive periods, preserved audit metadata), an upgrade with no terminal cases, the guard refusal for each table and a clean Down. The earlier Down tests that `TRUNCATE "ReviewRecords"` now name the lifecycle tables too, because `CaseClosures` references it.

## Schema-change procedure (project rule)

1. Read affected entities/callers, AppDbContext mappings and current migration history. Identify business cardinality, ownership, historical data and contract effects; ask about unresolved decisions.
2. Check query filters and write paths separately, including raw/bulk APIs and unfiltered membership/Identity sets. Preserve case locks and transaction ordering. Inspect DTO exposure.
3. Never edit `InitialCreate.TargetModel.cs` (the frozen original target model) and keep new migrations' target models independent of the snapshot. Modify entity/mapping together, inspect generated Up/Down/snapshot/SQL and unrelated schema churn. Do not use EnsureCreated to bypass migrations. Since `CaseLifecycleV2` the model snapshot is generated by `dotnet ef migrations add` and is not hand-patched; the earlier migrations' snapshot entries were patched by hand in the compact format.
4. Review backfill, nullability, locking, destructive operations, tenant-aware relationships, rollout and rollback. Do not rewrite an applied migration to achieve a new schema.
5. Test clean PostgreSQL migration and upgrade with existing rows, constraints, guard behaviour and cross-tenant negatives. Commit the migration and snapshot together.
6. Update authoritative persistence/domain/API docs only where behaviour or conventions changed, then run repository verification.
